## Architectural Distinctions: CSS vs Shading Languages

1. **CSS:** Browser stylesheet language executed by the layout and compositing engine for DOM elements and SVG. Properties like `transform` and `opacity` are often composited efficiently, but are not unconditionally GPU-backed.
2. **GLSL (OpenGL Shading Language):** Programmable shader language for WebGL 1/2 operating on rasterization pipelines within `<canvas>`.
3. **WGSL (WebGPU Shading Language):** Modern standard shading language for WebGPU pipelines supporting vertex, fragment, and compute shaders.
4. **"GPU Style Sheets" / GCC:** Strictly an **informal project shorthand**, not a W3C specification or browser API. Interface styling must use standard CSS; programmable graphics must use standard shaders.

## Starting Constraints vs Empirical Measurements

To avoid fabricated or overclaimed performance:
- **Starting Design Constraints (Tunable Rules of Thumb):**
  - DPR Cap: Clamp at `2.0` (or `1.5` on low-power profiles) to prevent mobile fillrate saturation.
  - Compositor Layer Budget: Aim for 8–16 active promoted layers per scene to prevent VRAM spikes.
  - Render-on-Demand: Default to dirty-flag rendering rather than unconditional 60fps loops.
- **Empirical Measurements (Require Target Device Profiling):**
  - Frame rates (FPS), frame times (ms), and frame drop counts.
  - Real User Monitoring (RUM) Core Web Vitals: p75 INP, LCP, and CLS.
  - VRAM footprint, memory pressure, and thermal throttling behavior.
  - Headless browser or software rasterizer (SwiftShader) tests must be reported as lab functional tests, never as hardware acceleration or performance proof.
