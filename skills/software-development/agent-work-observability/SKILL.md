# Live Agent Work Observability

Build operator dashboards that distinguish **observed execution**, **task alignment**, **verified correctness**, and **measured efficiency**. Never collapse these into an invented health score.

## Procedure
1. Trace the actual production page, API routes, and runtime event producer before redesigning. Identify which fields are live, static defaults, inferred, or delayed; preserve a working access path to old controls during an in-place replacement. Inventory the measurement sources that already exist before writing any new instrumentation: behavioral metrics usually live somewhere already (a capability/evidence table in a monitoring service, tool-call traces in the session store, a mutation ledger on disk). Query each with bounded reads and reuse it — a second collector for data that is already recorded creates two sources of truth that will disagree.
2. Inspect real payloads with bounded queries. Correlate event, tool, verification, and task records by trace/session ID. Scope the initial event, next-user boundary, and every subsequent message/tool query to the SAME session or run before applying ordering or limits; globally adjacent message IDs can belong to unrelated conversations and fabricate a task graph. Build nodes and durations only from observed events and timestamps; represent missing planner stages or elapsed measurements as unknown rather than inserting fictional stages or default milliseconds. For agent timelines, draw a shared time ruler and an explicitly labeled session-recording extent from observed start to recorded end or last observation; overlay short paired tool-call/result intervals, but never fill the intervening space as continuous work. Do not infer fork–join connectors, retries, thinking, or disconnection from timestamps alone; require explicit relation/event evidence. Treat `ACTIVE` database state or a recent message as insufficient evidence of a running agent when no recent runtime event exists.
3. Design the first viewport around four questions: what task is observed, what action just occurred and when, what evidence proves the result, and what remains unknown. Show source and freshness on each relevant status. On fetch failure or stale event, downgrade to `unknown`, not `online`. Enumerate each work source separately before claiming a unified background monitor: sub-agent registry, terminal process handle, and durable scheduler have different lifetimes and event channels. An empty sub-agent list does not imply no work is running. For long terminal jobs, expose a named process with live/running state and latest bounded output, then deliver its exit status; a completion-only notification is not a live progress display. If the current chat surface cannot stream that source, say so when starting it and provide an explicit way to check status, rather than promising automatic in-chat updates.
   - When the user supplies a motion/video reference for execution progress, inspect the actual clip at multiple timestamps before editing. Extract its *behavior* (moving observed-time playhead, overlapping sub-agent lanes, recorded fork/return), not merely the poster frame or visual palette; a static duration chart does not satisfy a live-progress request.
   - Trace the authenticated selector → root session → descendant-session API → event updates end to end. Rank selectable roots by recent observed activity or recent descendants, not only root start time; a long-lived chat may be older than every child in a limited recent-sessions list. Bound the query and keep profile isolation. For long-lived roots, render a recent observed-time window so current child intervals remain legible rather than compressing days into a few pixels. When a bounded descendant query exceeds its cap, order children by latest observed activity before applying `LIMIT`, include the truncation flag, and regression-test that the newest child survives while older children are pruned; otherwise a live monitor silently hides the work happening now.
   - Build the smallest working progression loop from an existing read-only snapshot endpoint: refresh only while the relevant view is visible, selected and authenticated; reconcile lanes by stable session ID in place, stop or back off on hidden/stale/disconnected states, and resume from a canonical snapshot without duplicate events. Test two snapshots with a new observed child/tool event and assert the display advances without full-panel blinking.
   - Place the playhead at or behind the latest *recorded* timestamp, never interpolate to `Date.now()` or treat a missing `ended_at` as proof that an agent is currently working. Draw fork links only from an explicit parent-session relation; never map child personas from task/prompt text or assume a delegation record belongs to a child without a deterministic key. If identity metadata is missing, use a neutral sub-agent label. Distinguish session-recording extent from observed tool intervals and never fill unobserved gaps as thinking, waiting, retry or continuous work.
4. Render untrusted summaries using `textContent`, not interpolated `innerHTML`; cap line length and sample sizes. Do not expose raw tool arguments, payload JSON, secrets, or private messages on a public dashboard. A page showing behavioral metrics (correction rate, typo rate, working habits) is private data even when it looks like a neutral dashboard: bind the service to `127.0.0.1`, not `0.0.0.0`, and proxy it through the existing authenticated path. "Put it on my domain" is not authorization to publish it — verify with an unauthenticated request that returns 401/303, not 200.
5. Label measurements precisely: tool success is not code correctness; tool p95 is not code efficiency; RAM usage is not token spend; recorded verification for another trace is not proof for the current task. If alignment with the user's request is not assessed against explicit criteria, say `belum dapat dinilai`. A capability with no supporting evidence is rendered `INSUFFICIENT DATA`, never a score: one fabricated number discredits every other number on the page. A high count of unmeasured capabilities is itself a useful finding about how deeply the system has been exercised.
6. Verify the public URL in a browser at desktop and mobile widths after asynchronous data loads; inspect populated fields, connection state, and horizontal overflow. Inspect the FULL mobile screenshot before cropping details: device-pixel-ratio screenshots have more image pixels than CSS viewport pixels, so a viewport-sized crop falsely resembles clipped content. For a video-inspired timeline, inspect early/middle/final source frames, then verify static composition, actual playhead motion/scrubbing, and interactions independently. Assert visible span count, tick labels, tiny-event footprint, truthful status, and responsive hierarchy; test a realistic long-running session, not only a compact synthetic fixture. A full suite with exit 0, HTTP 200, or a clean fixture screenshot proves neither usefulness nor authenticated WebView appearance. Mark authenticated-client verification NOT RUN when inaccessible; never report product acceptance from a fixture alone. If the user rates the result poorly, revisit the screen's single purpose and reference behavior instead of moving old panels or polishing the same chart. Exercise stale/disconnected rendering and preserve access to underlying evidence. Do not preserve unrelated controls on a surface the user explicitly scoped to one feature; retain their backend and data only if requested.
7. Render charts server-side as inline SVG. It needs no chart library, survives a dead CDN, and works with JavaScript disabled — for an internal dashboard this outlasts pulling in a rendering library. Assert in the chart tests that every generated coordinate falls inside the `viewBox`, and cover the cases that break a naive renderer: a flat series (division by zero), an out-of-range value (clamp to the axis bound), and fewer points than the chart needs (emit a message, not a malformed path). When such a test fails, check the assertion before the renderer — a bar at maximum value legitimately equals the canvas width, and editing the code to satisfy a wrong assertion introduces a real bug.
8. **Hierarchical Subagent Tree Monitoring (Transparansi Nyata):**
   - Sediakan panel/window visual di samping area obrolan (`SubagentTreeMonitor`) untuk memantau kapasitas konkuren yang tersedia, jumlah Anak (Level 1), jumlah Cucu (Level 2+), status live (Bekerja, Selesai, Gagal), dan perkakas aktif. Pengguna harus dapat menyaksikan status dan progres agen secara transparan melalui panel monitor, bukan sekadar dipaksa percaya pada klaim teks laporan akhir.
9. **Zero-Scroll TUI & Zen Response Architecture (Claude Code / OpenCode Style):**
   - **Active Skill Shelf (`⚡ Skill`)**: Deklarasikan seluruh skill yang aktif pada turn tersebut di bagian teratas respon (`⚡ Skill <nama> — <peran>`) agar pengguna mengetahui panduan/doktrin yang sedang memandu agen.
   - **Shell Command Card**: Tampilkan eksekusi perintah terminal dengan format `# <deskripsi tugas>` diikuti perintah tebal dan stdout bersih tanpa wrapper berlebihan.
   - **Tool Activity Indicator**: Tampilkan penanda aksi akses file ringkas satu baris (`→ Read <path>`, `→ Edit <path>`).
   - **Batas Keras Diff 20 Baris (Side-by-Side Hunk Box)**: Perubahan kode wajib disajikan per-hunk/metode (bukan satu file utuh panjang) dengan format side-by-side (kiri: baris lama merah `-`, kanan: baris baru toska `+`) dan nomor baris ganda presisi. Batasi tampilan maksimal 20 baris per-hunk; jika melebihi, potong baris ke-19 dan tampilkan keterangan ringkas `... [+ N baris disembunyikan, total M baris]`.
   - **Dynamic Task Checklist**: Tampilkan alur rencana kerja multi-langkah dengan status tegas: `[✓]` selesai (abu-abu), `[ ]` langkah aktif (hijau/toska tebal), dan `[ ]` antrean (abu-abu).
   - **Penalaran Internal Ringkas (CoT)**: Penalaran internal wajib tampil sebagai animasi loading satu baris saat live, dan diringkas satu baris (`◈ Nalar (1.4s · 312 tok)`) saat settled. Dilarang menggelontorkan ratusan baris nalar mentah yang membanjiri ruang obrolan.
   - **Zero Conversational Slop**: Langsung sajikan aksi teknis nyata dan artefak kerja; hilangkan kalimat pembuka/penutup basa-basi AI. Rujukan implementasi lengkap ada di `references/zen-tui-spec.md` dan `scripts/zen_tui_engine.py`.
10. **Pusat Log Galat Tunggal (Centralized Error Log Detection):**
    - Saat menguji atau membuat kode baru, dilarang menebak atau mencari galat secara acak di sembarang berkas. Pemeriksaan wajib langsung merujuk pada pusat log error sistem (`~/.hermes/logs/errors.log`, log servis PM2 `~/.pm2/logs/`, atau keluaran compiler/test runner) untuk menemukan akar masalah (*root cause*) secara cepat dan presisi.

## Operator controls and simple interfaces
- Inventory each requested action against the actual runtime adapter before exposing its button. Record the target process/session and the measurable effect: changing a stored status label is not stopping an agent, and pausing new worker admission is not pausing already-running work. Verify registry ownership and transport binding; starting another process with the same session ID does not grant control over an existing process-local agent registry.
- Keep unsupported actions visible with an explicit reason when needed for feature completeness, but never return success for a no-op. Verify a permitted action through the executor and independent readback, not only through a UI status update. Do not silently replace control of existing agents with separately managed workers and call the original requirement complete.
- Treat Bagas's confusion about usage as a workflow defect, not a request for another technical feature tour. Explain the immediate next tap first; in the interface, prioritize the real sequence **Buat tugas → Setujui → Baca hasil** over the execution graph. Use plain Indonesian action/status labels and keep worker IDs, PIDs, protocol names and raw logs in technical details. Offer a short replayable guide without blocking experienced users; examples may fill a form but must not execute work automatically.
- Keep the first mobile screen simple and move details into focused views or drawers without dropping requested functions. Track graph, controls, approvals, reader, and telemetry separately in the written acceptance ledger; a polished subset is not a complete control surface.
- Derive approval counts and buttons from the same current eligibility predicate, not from all records of a managed-worker type. Include a completed/running record and a pending actionable record in the same fixture; only the latter should count as awaiting a decision, because historical records otherwise appear approvable again.
- Keep results associated with one selected task and recover them from its server record after refresh. Do not append the entire saved output of every task on each status poll; repeated refreshes must neither duplicate lines nor mix task results. Expose the result-reading action where the user sees completion, rather than requiring discovery of a combined diagnostic log.

Use the HTTPS fixture and scrolled-mobile interaction recipe in `references/control-surface-verification.md` when testing authenticated, streaming control dashboards.

Prefer existing runtime endpoints and a bounded refresh mechanism over a new polling service. Measure before claiming lower token use, latency, or improved developer visibility. Reuse evidence while its source hashes and dependencies remain unchanged; rerun only the gate affected by a new edit, a concrete missing criterion, or the requested final acceptance. Classify late worker notifications against the artifact version already accepted: an earlier timeout is not a regression of a later verified release, and an unchanged notification does not warrant another status message. Summarize what is verified and what the instrumentation still cannot see in a few weighted points, not a feature tour.
