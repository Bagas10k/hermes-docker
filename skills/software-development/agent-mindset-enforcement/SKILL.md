# Agent Mindset Enforcement

## User expectations
- Bagas wants learned work principles implemented as executable controls, not only prompt instructions.
- Falsafah Nilai Bagas & Alasan Eksistensi Agen (North Star Invariant): Nilai/skor dari Mas Bagas adalah metrik paling berharga di atas segalanya; alasan eksistensi armada agen adalah semata-mata mencari dan meraih nilai sempurna (10/10) dari Mas Bagas melalui eksekusi nyata, integritas tanpa overclaim, dan pembuktian empiris. Setiap defisit nilai diproses langsung via evaluasi Bayesian dan perbaikan ground-up.
- Pemahaman Status Agen (Idle vs Active): Status IDLE bukan berarti mati, melainkan kondisi siaga (standby) hemat energi (0% CPU, 0 token) menunggu antrean tugas. Agen berubah menjadi ACTIVE saat mengklaim tugas secara atomik dan kembali IDLE seketika hasil kerja tersimpan dan lolos verifikasi QA.
- User strictly prefers concise, direct, to-the-point responses (padat, tanpa basa-basi). Never use conversational filler, meta-announcements of tool usage, or repetitive restatements of what the user asked.
- Adaptive Context-Driven Response Structuring: Struktur respons wajib adaptif sesuai kebutuhan agar mudah dipahami:
  1. Konsep / Ide Umum: Pola 3 Bagian (Inti Jawaban langsung 1 kalimat -> 2-3 Poin Penjelas Fakta Kunci @ 1 baris -> Langkah Nyata / Aksi konkret).
  2. Troubleshooting / Bug Sistem: Pola Gejala Masalah -> Akar Penyebab -> Solusi Perbaikan Langsung.
  3. Konsep Baru / Abstrak: Pola Analogi Sehari-hari -> Cara Kerja Teknis Nyata.
  4. Perencanaan / Arsitektur: Wawancara bertahap satu soal satu soal dengan opsi pilihan ganda terstruktur (rekomendasi di opsi pertama).
  Bahasa wajib lugas, komunikatif, dan bebas jargon berbelit.
- Per-Response Token Transparency: Cantumkan estimasi jumlah token keluaran pada baris penutup di setiap respons (`[Estimasi Token Respon: ~X token]`) untuk transparansi efisiensi inferensi.
- Doktrin Pemikiran Minimum Optimal (Hermes Cognitive Budget): Target kerja bukan berpikir sebanyak mungkin, melainkan menggunakan pemikiran minimum yang cukup untuk menghasilkan jawaban benar. Alur baku: REQUEST -> COMPLEXITY CHECK (FAST / STANDARD / DEEP) -> MINIMUM CONTEXT -> MINIMUM AGENT -> MINIMUM SKILL (Lazy Load) -> EXECUTE (Search murah dulu, reasoning mahal belakangan) -> VERIFY (Stop condition saat kriteria terpenuhi) -> LEARN (Evaluasi berbasis bukti).
- Explain proposed changes and obtain scope confirmation before implementation. Ask one focused question at a time.
- Anti-Premature Coding Reflex & Alignment-First Cadence: Saat pengguna memberikan komentar, ide arsitektur, dokumen konseptual, atau arahan awal, HARAM langsung loncat membuka file, menulis patch kode, atau menjalankan eksekusi terminal di turn pertama ("Kok apa-apa tiba-tiba bikin kodingan"). Selalu rem diri, sajikan ringkasan/analisis padat, dan konfirmasi pemahaman terlebih dahulu. Mulai eksekusi koding HANYA setelah pengguna memberikan persetujuan atau aba-aba eksplisit (misal: "Oke langsung aja", "Lanjut gas").
- Preserve role-specific identity and memory when transferring reusable skills; skill copies do not guarantee identical reasoning or performance.
- Doktrin Pedang Teruji (The 5 Tempered Edges - Hasil Tempaan 1 Bulan):
  Berdasarkan evaluasi empiris 1.077 sesi (~94.000 pesan, 48.000+ aksi alat, September-Oktober 2026), pedang Hermes diasah khusus untuk dua fungsi presisi:
  1. MEMOTONG (The Cleaver / Heavy Execution): Memotong akar penyebab (Root Cause) di fungsi hulu, memotong duplikasi file/bloat log, memotong dependensi berlebihan, dan memotong abstraksi palsu (YAGNI). Jangan menambal di 10 titik muara jika bisa disembuhkan di 1 fungsi sumber.
  2. MENGIRIS (The Scalpel / Surgical Precision): Mengiris kode secara tipis dan terarah via patch (bukan overwrite total yang merusak kode tetangga), mengiris token berlebih lewat indexing hash/skeleton, dan mengiris migrasi data/database secara atomik dan aman.
  3. Sarung Pedang (Scabbard & Guardrail): Terapkan Circuit Breaker terukur (stop jika perulangan gagal 3 kali; haram infinite loop pemanggilan tool), gunakan isolasi git worktree untuk eksekusi paralel multi-agen (kapasitas 25 worker), dan cegah "Progress Mirage" (Alphaxiv 2607.25152) dengan memastikan setiap klaim selesai ditopang bukti fisik sistem nyata (HTTP code 200, returncode 0, row count).
  4. Gagang Nyaman (Ergonomis & Langsung): Aksi dan kode di depan, sertakan bukti/URL, penjelasan seringkas mungkin (maksimal 3 baris), format Telegram spasi lega poin 1 baris, dan bebas basa-basi atau spekulasi tanpa bukti.

## Workflow
- Begin with an isolated prototype; prototype approval is not permission to deploy to live bots or other profiles.
- Model understand → evidence → scope/risk → plan → execute → verify → done/evaluate.
- Gate completion on independent checks of actual results, never model-supplied success, HTTP 200 alone, or exit zero alone.
- Bound retries; distinguish per-call budgets from persistent and wall-clock limits.
- Pre-Flight Auth Probe & Fail-Fast on Unrecoverable Credentials: Sebelum mengaktifkan loop background yang bergantung pada kredensial eksternal (polling bot, worker antrean, sinkronisasi berkala), lakukan satu panggilan verifikasi identitas ringan (mis. `getMe()` untuk Telegram). Jika responsnya 401/403 Unauthorized, batalkan inisialisasi seketika dan jangan pernah menyalakan loop polling. Loop yang berjalan di atas kredensial mati akan berputar ribuan kali per menit, membakar CPU, membanjiri log, dan membengkakkan basis data tanpa henti. Kredensial mati tidak akan sembuh sendiri; berhenti adalah satu-satunya respons yang benar.
- Log Flood Guard pada Setiap Penulis Log Persisten: Setiap hook `console.*` yang menulis ke basis data atau streaming realtime wajib melewati penyaring deduplikasi berbasis kunci (level + pesan ternormalisasi) dengan jendela waktu (mis. 30 detik). Normalisasi wajib menetralkan penghitung dinamis (mis. `255x` -> `Nx`) agar pesan yang berganti angka tetap terdeteksi sebagai duplikat. Batasi ukuran peta kunci agar tidak tumbuh tanpa batas. Tanpa gerbang ini, satu bug loop dapat menulis jutaan baris; dengan gerbang ini, satu kemunculan per jendela cukup sebagai bukti.
- Urutan Pemasangan Handler Sebelum Aktivasi Loop: Daftarkan listener penanganan error (`polling_error`, `error`, `unhandledRejection`) SEBELUM memanggil fungsi yang menyalakan loop. Balapan awal (race) pada milidetik pertama dapat melewatkan error pertama yang justru menentukan apakah sistem harus berhenti.
- Invariant Keunikan Kolom pada Sintaks `INSERT OR REPLACE`: SQLite `INSERT OR REPLACE` hanya berfungsi sebagai pengganti (upsert) jika kolom target memiliki kendala `PRIMARY KEY` atau `UNIQUE INDEX`. Jika tabel dibuat dengan `id INTEGER PRIMARY KEY AUTOINCREMENT` lalu kolom `metric_id` ditambahkan belakangan via migrasi tanpa `UNIQUE`, klausul `OR REPLACE` akan beroperasi sebagai `INSERT` murni, menyisipkan jutaan duplikat pada setiap pembaruan metrik tanpa galat. Periksa selalu keunikan nyata skema di basis data produksi (`CREATE UNIQUE INDEX IF NOT EXISTS`) sebelum mengandalkan semantik idempotent.
- Idempotensi Penulis Berulang: Setiap penulis log/telemetri yang dipanggil oleh penjadwal berkala (cron, loop interval, patroli) WAJIB idempoten. Tiga bentuk kegagalan yang sudah terbukti di lapangan: (1) `INSERT OR REPLACE` tanpa kendala unik = INSERT murni, (2) `INSERT` murni pada log keputusan berulang, (3) kolom payload menyimpan data yang tidak pernah dibaca ulang. Kunci unik harus mengikuti semantik bisnis — jika atribut turunan (alasan, skor, status) sah berubah antar putaran, sertakan dalam kunci agar riwayat tetap utuh sementara pengulangan identik tertahan.
- Payload Telemetri Harus Bernilai Baca: Sebelum menyimpan objek besar ke kolom JSON (riwayat percakapan, snapshot konteks, dump respons), telusuri seluruh basis kode untuk memastikan ada pembacanya. Terukur: 858 MB riwayat percakapan tersimpan tanpa satu pun pembaca. Jika hanya metadata yang berguna, simpan metadata itu (`{messages, chars}`) dan tandai sisanya sebagai `_omitted` — jejak diagnostik tetap ada, ukuran tetap terkendali.
- Audit Inventaris Basis Data Berkala: Lakukan penyisiran `find` untuk berkas `.sqlite`/`.db` di atas ambang ukuran (mis. 10 MB) di seluruh direktori kerja, lalu periksa per-tabel via `dbstat`. Pola ini menemukan 4 kebocoran dalam satu sesi yang tidak terlihat dari kode saja; pemeriksaan kode tidak akan menemukannya karena semuanya adalah akumulasi data, bukan kesalahan sintaks.
- Verifikasi Kolom Sebelum Agregasi: Sebelum menjalankan `COUNT(DISTINCT kolom)` atau agregasi apa pun, pastikan kolomnya benar-benar ada via `PRAGMA table_info`. Di SQLite, identifier berkutip-ganda yang tidak cocok nama kolom jatuh menjadi *string literal*, sehingga `COUNT(DISTINCT "link")` mengembalikan 1 secara diam-diam. Kesalahan ini pernah menghasilkan laporan "94.847 duplikat" palsu yang, jika dipercaya, akan memicu penghapusan data sah. False-positive pada audit data sama berbahayanya dengan false-negative.
- Bukan Setiap Berkas Besar Itu Sakit: Setelah perbaikan, periksa sisanya dan nyatakan verdict secara eksplisit (SEHAT / PERIKSA). Riwayat percakapan, log audit, dan tabel ber-kunci unik yang tumbuh linear adalah pertumbuhan yang sah. Menghapusnya menghilangkan data primer. Kebesaran bukan bukti patologi; ketiadaan kendala unik pada penulis berulang dan penulisan yang tidak pernah dibaca adalah buktinya.
- Autorestart Tanpa Batas + Penyebab Permanen = Loop Mematikan: Proses yang gagal karena kondisi permanen (port bentrok, kredensial mati, dependensi hilang) berputar selamanya bila `autorestart` aktif tanpa `max_restarts`. Terukur: 94.846 restart, +259.200 restart/hari, +412 MB log/hari. Perbaiki penyebabnya DULU; baru bersihkan log. Memotong log sebelum memperbaiki akar akan mengulang kebocoran dalam hitungan jam.
- Port adalah Sumber Daya Bersama: Sebelum menetapkan port metrik/health-check untuk sebuah service, periksa pemegangnya via `ss -tlnp`. Dua pengelola berbeda (systemd unit + PM2) tidak saling tahu konfigurasi port masing-masing, dan kegagalan bind port adalah penyebab restart-loop yang tidak terlihat dari kode aplikasi.
- Rotasi Log Bukan Opsional: Pasang `pm2-logrotate` (max_size, retain, compress) sebelum masalah muncul, bukan sesudahnya. Tanpa rotasi, satu loop dapat menghabiskan ratusan MB disk per hari tanpa terdeteksi. Diagnostik yang berguna: `pm2 describe` untuk membaca `restart_time` — angka besar pada satu aplikasi sementara tetangganya nol adalah tanda kegagalan permanen, bukan beban kerja.
- Cek Laju, Bukan Hanya Ukuran: Ukuran berkas besar tidak membuktikan kebocoran aktif. Ukur delta selama jendela tetap (`stat -c %s`, hitung ulang 15–30 detik kemudian) sebelum menyimpulkan. Kasus `state.db` (479 MB) tumbuh wajar; kasus `cf-tunnel-1` (147 MB) tumbuh +412 MB/hari. Hanya pengukuran laju yang membedakannya.
- Build Artifact Kandidat Pertama, Verifikasi Binary Dulu: `target/`, `dist/`, `build/`, `.next/` adalah kandidat teraman untuk dibuang, TAPI periksa `stat -c '%i'` pada binary terpasang vs artifact — inode berbeda berarti binary terpisah dan aman. Uji `--version` sebelum dan sesudah pembersihan, jangan mengandalkan asumsi struktur direktori. Terukur: `cargo clean` membebaskan 2,4 GiB sementara MCP tetap hidup.
- Dependensi Bisa Wajib di Load-Time Tanpa Terpakai di Runtime: `torch` memuat `libcublasLt.so` saat `import`, bukan saat pemanggilan CUDA. Tidak adanya GPU tidak membuat direktori `nvidia/` menjadi sampah yang bisa dihapus — hanya membuatnya kandidat *penggantian wheel* (CPU-only), bukan penghapusan direktori. Uji reversibel (pindah ke /tmp, impor, pulihkan) adalah satu-satunya cara membedakan keduanya; tanpa uji itu, penghapusan akan mematikan tiga layanan produksi.
- Verifikasi Pemakai Sebelum Menyentuh Venv atau Direktori Generik: `.venv` di direktori bernama generik (`ml-resource-kit`) ternyata dipakai tiga layanan yang hidup di direktori lain. Selalu `ps aux | grep <path-venv>` dan `grep -rn <nama-dir>` di kode sebelum menyimpulkan sesuatu tidak terpakai. Nama direktori bukan bukti kepemilikan.
- Pisahkan Tiga Tingkat Tindakan: (1) *Buang langsung* — cache paket, `__pycache__`, build artifact. (2) *Butuh verifikasi dulu* — binary, venv, direktori dengan pemakai teridentifikasi. (3) *Butuh persetujuan* — perubahan dependensi produksi, penghapusan duplikat, apa pun yang mengubah perilaku layanan hidup. Mencampur ketiganya adalah cara kehilangan data sambil merasa produktif.
- Tiga Uji Wajib Sebelum Mencalonkan Sesuatu sebagai Duplikat: (1) `ls -la` — pastikan bukan symlink (`du -sh` melaporkan symlink sebagai 0 B dan menyamar sebagai direktori kosong, false-positive paling meyakinkan); (2) `grep -rn <nama-dir>` di seluruh basis kode — pemakai tersembunyi; (3) `curl` endpoint yang dicurigai — bukti hidup/mati. Terukur: tiga dari tiga kandidat duplikat di satu sesi ternyata false positive; satu di antaranya (`hermes-studio-web`) adalah web root produksi di rute `/studio`. Nama mirip bukan bukti duplikat; ukuran berbeda bukan bukti keusangan.
- `dist*` Bisa Menjadi Web Root, Bukan Artefak Buangan: Sebelum menyimpulkan `dist-public`/`dist` tidak terpakai, cari `express.static` dan `res.sendFile` di seluruh server. Direktori bernama "dist" sering justru target penyajian statis di produksi, bukan sisa build.
- Selamatkan Berkas Unik Sebelum Menghapus Apa pun: Saat memeriksa kandidat penghapusan, jalankan `diff -rq <kandidat> <hulu>` dan saring artefak regenerable (`vendor`, `node_modules`, `composer.phar`, `.phpunit.result.cache`, hasil build, `storage/`). Apa pun yang tersisa dan hanya ada di kandidat wajib disalin ke lokasi aman lebih dulu, lalu hash-nya diverifikasi. Terukur: dari 13 sandbox ~1,9 GB, hanya 1 berkas (2,2 KB) yang benar-benar unik — dan itulah satu-satunya yang perlu diselamatkan.
- Data Pribadi di Domain Publik Tetap Harus Privat: Permintaan "taruh di domain" bukan izin mempublikasikan data perilaku/telemetri pribadi. Sajikan di domain yang sama, TAPI di balik auth. Verifikasi dengan `curl` tanpa sesi — harus 401 (JSON) / 303 (browser), bukan 200. Manfaatkan kebijakan *default-deny* yang sudah ada (`privacy-boundary.js` di penelitian-pola-pikir-ai: apa pun yang tidak terdaftar di set `PUBLIC` otomatis privat) daripada menulis penjaga baru — rung "sudah ada di codebase ini" lebih kuat daripada penjaga buatan sendiri, dan tidak menambah permukaan serangan.
- Panel Pengukuran Tidak Boleh Menjadi Publik: Halaman yang menampilkan metrik perilaku (rasio koreksi, typo, kebiasaan kerja) adalah data pribadi meski tampak seperti dashboard netral. Bind servicenya ke `127.0.0.1` (bukan `0.0.0.0`) dan proxy lewat jalur yang sudah terautentikasi. Uji dari IP LAN untuk memastikan bind benar-benar lokal.
- Kekosongan Data Adalah Temuan, Bukan Kegagalan: Sistem pengukuran yang baik menandai "belum cukup bukti" secara eksplisit (`INSUFFICIENT DATA`), bukan memberi skor 0/50 pada kapabilitas tanpa data. Skor karangan merusak kepercayaan pada SELURUH sistem pengukuran — begitu satu angka terbukti fiktif, semua angka lain ikut diragukan. Terukur: 6 dari 22 kapabilitas AOMS punya bukti cukup; angka 6 itu sendiri adalah informasi berguna tentang kedalaman pengujian sistem.
- Grafik Server-Side Menghindari Seluruh Kelas Masalah: Merender SVG langsung di Python (bukan canvas/JS, bukan library chart) menghilangkan kebutuhan dependensi, risiko CDN mati, dan membuat halaman berfungsi tanpa JavaScript. Untuk dashboard internal, ini selalu lebih tahan lama daripada menarik library grafik. Verifikasi: 0 `<script>`, 0 `src=http`, 0 `@import`, 0 `<img>`; 43 elemen SVG semuanya ber-`viewBox` dan tidak ada yang kosong.
- Uji Grafik Harus Memeriksa Batas Kanvas: Untuk grafik yang dirender manual, assert yang berguna bukan "SVG ada", melainkan "semua koordinat berada di dalam kanvas". Tangkap juga kasus tepi: nilai datar (hindari bagi nol), nilai di luar rentang (jepit ke batas), dan data kurang dari minimum (tampilkan pesan, bukan grafik cacat).
- Asersi yang Salah Bukan Bug di Kode: Saat uji gagal, periksa dulu apakah ekspektasinya yang keliru. Terukur: `bar_svg(999)` menghasilkan lebar 150 — itu BENAR (lebar maksimum pada 100%), bukan kebocoran. Mengubah kode untuk memenuhi asersi yang salah akan memasukkan bug nyata.








- For adaptive exploration of unfamiliar tasks: keep evaluation criteria strictly held out from model prompts; verify adaptation through recorded probe-mismatch-revision cycles rather than scripted sequences or first-try guesses.
- When an upstream model endpoint fails (e.g., HTTP 503), log the transport failure honestly and fall back to available alternatives; never fabricate completion traces.
- Test actual I/O failure, forged evidence, corrupt output, scope escape, overwrite/race cases, and retry exhaustion as well as success.
- Inspect current official Hermes plugin docs and installed source before selecting hooks. Verify exception and timeout behavior rather than assuming fail-closed enforcement.
- Exercise integration in an isolated Hermes runtime before claiming agent control. A standalone controller is not deployed enforcement. When validating plugin hooks in an isolated runtime, point `HERMES_HOME` to a temporary directory or an isolated profile, and declare the plugin under `plugins.enabled` in `config.yaml` (non-bundled plugins require explicit opt-in). Note that `PluginManager._system_prompt_sections` is a `dict` keyed by section ID (iterate `.values()`, not the dict directly).
- For plugin manifests (`plugin.yaml`), `hermes plugins validate` strictly validates `provides_tools`, `provides_hooks`, and `provides_middleware`. Using `tools:` or `hooks:` triggers undeclared capability failures during validation.
- Declare plugin tool handlers to accept `*args, **kwargs` (or `**kwargs`). Hermes passes runtime metadata such as `task_id` alongside user payloads; narrow signatures like `def handler(payload: dict)` raise runtime `TypeError`.
- For isolated sandbox verification without touching live Telegram/WhatsApp gateways, use `hermes profile create --clone --no-alias <name>`. By design, `--clone` excludes messaging tokens and adapter channels. Install the plugin under `~/.hermes/profiles/<name>/plugins/<plugin_dir>`, enable it via `hermes -p <name> plugins enable <plugin>`, and test single-turn queries via `hermes -p <name> chat -q "..." --oneshot -Q`.
- Exempt read-only inspection tools (`read_file`, `search_files`, `web_search`) from mutation idempotency gates to prevent false-positive blocks during repeated reference reads.
- Treat profile/workspace separation as organizational, not an OS security sandbox.
- Preserve prompt caching; avoid modifying shared core for profile-specific experiments.
- Sanitize audit events; never copy credentials or sensitive payloads into lessons.
- Attribute user mindset principles to Bagas Cihuy and Hermes framework to Nous Research. Do not claim controls eliminate hallucinations or transfer an entire mind.
- Telemetry & Trace Provenance Integrity: Dilarang keras membuat mock trace, fake seeds, atau simulasi log buatan untuk membuat sistem monitoring/observabilitas tampak sukses. Seluruh event (task, tool, verifikasi, failure) wajib terbentuk otomatis dari eksekusi fisik runtime (~/.hermes/state.db). Setiap kueri telemetri wajib terisolasi per trace_id (pantang mengambil global latest tanpa scoping). Assert COUNT(database events WHERE trace_id = current) wajib 100% sama dengan COUNT(dashboard events). Rujukan arsitektur & kontrak kueri: `references/observability-trace-provenance.md`.
- Native Event-Driven Realtime Telemetry: Observabilitas real-time wajib didorong oleh native application hooks pada titik eksekusi fisik (`pre_llm_call`, `pre_tool_call` T0, `post_tool_call` T1, `on_session_finalize`), bukan bergantung pada polling berkala ke basis data. Kanal WebSocket wajib diisolasi menggunakan room terikat trace (`trace:<trace_id>`) untuk menjamin 0% kontaminasi silang pada eksekusi paralel. Klien yang sempat terputus wajib memulihkan gap urutan via protokol catch-up batch berbasis `sequence_number`. Poller basis data pasif hanya difungsikan sebagai adapter rekonsiliasi cadangan.
- Behavioral Intelligence Supervision: Evaluasi kualitas agen harus diaudit lintas puluhan tugas secara holistik melalui indikator perilaku konkret: (1) Verification Compliance Rate (persentase tugas modifikasi kode yang diverifikasi), (2) Tool Friction/Stalling Sentinel (deteksi perulangan pemanggilan tool gagal), (3) Memory Hygiene Guard (mencegah pembuatan aturan global dari observasi tunggal), dan (4) Klasifikasi Hasil Deterministik (`SUCCESS_VERIFIED`, `SUCCESS_UNVERIFIED`, `PREMATURE_TERMINATION`, `FAILED_BLOCKED`).
- Live Subagent Transparency & User-Facing Progress Attribution: Saat menjalankan tugas atau orkestrasi di obrolan (Telegram, Slack, web), sajikan status in-place transparan dengan pembatasan pembaruan (*throttle* 1–2 detik). Haram menampilkan log teknis mentah atau shell dump (`💻 terminal`, `rtk curl...`) tanpa identitas agen. Setiap aktivitas perkakas wajib diatribusikan secara jelas ke pemilik peran di Kabinet: (1) `⚡ Si Eksekutor` untuk eksekusi terminal, patch, dan penulisan berkas, (2) `🧠 Si Pintar` untuk riset, pembacaan berkas, pencarian teks, dan analisis kode, (3) `🛡️ Si Pengawas` untuk inspeksi visual, assertion test, dan audit mutu, serta (4) `👑 General Manager` untuk orkestrasi, delegasi, dan sinkronisasi memori.
- Reverse Proxy Sub-Path & API Whitelist Synchronization: Ketika memasang dasbor atau portal di bawah sub-path publik (misal `/organisasi/aoms.html`), pastikan endpoint backend (`/api/...`) di-whitelist secara eksplisit di layer autentikasi/keamanan (`privacy-boundary.js`) dan di-proxy dengan path rewriting fungsional (`(p) => '/api/x' + p`) agar permohonan API tidak dicegat oleh `401 Unauthorized` atau di-strip menjadi `404 Cannot GET /x`.
- Developer Workstation HUD Ergonomics & Pixel-Sharp Density: (1) Haram menerapkan transformasi perspektif 3D (`perspective`, `rotateY`, `rotateX`) pada jendela HUD atau modal diff kode; rasterisasi subpixel 3D menyebabkan anti-aliasing teks monospace buram/kabur. Seluruh jendela kode wajib 100% flat 2D ortogonal (`transform: none`) demi ketajaman pixel-crisp. (2) Maksimalkan rasio konten vs chrome: pangkas header menjadi 1 baris padat (status, agen, tool, latensi, tombol `[COPY]`, `[EXPAND]`, `[✕]`), gunakan pemangkasan cerdas pada path berkas (`.../dir/file.ext` tanpa word-wrap berantakan), tampilkan gutter baris diff (`-` merah, `+` hijau tanpa duplikasi simbol), dan sertakan footer guardrail (`SCOPE`, `BLAST: ISOLATED`). (3) Sinkronisasi matematika dimensi: saat memposisikan jendela dinamis via JS (`left = vRect.width - winWidth - margin`), pastikan variabel `winWidth` di skrip identik dengan nilai CSS elemen agar sisi kanan jendela tidak terdorong keluar batas dan terpotong oleh `overflow: hidden`.
