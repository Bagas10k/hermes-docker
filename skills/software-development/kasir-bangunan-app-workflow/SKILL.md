# Kasir Bangunan prototype workflow

## When to Use

Load for changes or diagnostics in `/home/ubuntu/kasir-bangunan-app`, especially login, sidebar, and public subpath routing.

- Repository: `/home/ubuntu/kasir-bangunan-app`; public test URL: `https://www.jajandigital.web.id/kasir-bangunan/`. Distinguish prod, demo, stage, and disposable test containers/databases before changing an account or data. Bagas requires stable authentication credentials across dashboard revisions: do not modify auth, recreate users, switch DBs, or reset account data during unrelated UI/feature changes. Never infer an account exists from a previous chat; query the *currently served* database for non-secret columns and read it back after creation. Never store, quote, or reuse a demo password in this skill.
- Laravel lives under a reverse-proxy subpath. The login form action and `route('pos.index')` must retain `/kasir-bangunan`; `redirect()->intended(...)` can honor a stale `url.intended` such as the domain root even when route generation is correct. Reproduce with `tests/Feature/SubpathRoutingTest.php` using `url.intended` set to the domain root and verify the resulting `Location`. Explicitly clear intended destination and use the named POS route when login should always land in the app.
- For isolated regressions use `kasir-e2e-preview` with `DB_CONNECTION=sqlite DB_DATABASE=:memory: DB_URL= APP_ENV=testing SESSION_DRIVER=array`; never run mutating tests against the active DB. For visual fixtures, use a disposable SQLite file under `/disposable/` and verify effective Laravel connection before migration/seed. POS's `confirmCheckout()` invokes native `form.submit()`, which bypasses global submit listeners: normalize any new `data-currency-input` fields explicitly before that call and test a comma-decimal value in a real browser. Never execute ad-hoc fixture scripts that call `migrate:fresh` inside `kasir-bangunan-prod-app-1`: in that container, `putenv('DB_CONNECTION=sqlite')` followed by Laravel bootstrap still resolves to `mysql:kasir_bangunan_prod` because Compose process environment wins. Guard BEFORE any mutation by asserting `config('database.default') === 'sqlite'` and actual database path `:memory:`; run only in a disposable container, then recheck active DB counts. A successful test, PHP lint, Vite build, public login HTTP 200, or a generated route does *not* by itself prove an authenticated public browser session works. If no saved browser-vault login is available, disclose this limit instead of typing a password into browser automation.
- The sidebar in `resources/views/layouts/app.blade.php` is a separate scroll container from `.app-main`. Hide only the sidebar's scrollbar (`scrollbar-width: none` plus `::-webkit-scrollbar`), not its `overflow-y: auto`; verify `scrollTop` changes while its bounding top remains fixed when main content scrolls. Bypass stale browser HTML cache when inspecting fresh inline CSS.
- For an authorized schema change, verify the effective database name and current row counts first; take a private `mariadb-dump --single-transaction` backup and validate `gzip -t` plus table count, then run `php artisan migrate --force --path=<single migration>` (never `migrate:fresh`). Read back migration status, columns/FK, account and transaction counts, and the served login/subpath. A valid dump is not a tested restore.
- Finish the *feature*, not just the migration: inspect prerequisites such as active vehicles, products, stock, and posted opening balances. When dummy data is authorized, use neutral synthetic master records only as needed, start products at zero stock, and read them back; do not fabricate stock or seed sales/receipts/journals into the active ledger merely to make a demo look complete. Use isolated SQLite tests for sale/receipt with and without fleet plus cash/stock rollback, then a real authenticated browser flow if credentials are available through the vault. If no vault login exists, mark that exact browser gate untested instead of declaring public checkout complete.
- For financial-report readiness, audit the dependency chain **COA → posted opening balance → receipt/stock journal → sale/COGS → ritase/expense → P&L → balance sheet**. Read the currently served DB and establish baseline row counts plus a deterministic hash of historical journal lines. If canonical COA is empty while journals exist, back up and add only missing canonical master accounts, then read back the same journal hash and report totals; never seed transactions to manufacture nonzero reports. Write a failing isolated test before a money-path fix, covering per-entry debit=credit (opposing bad journals must not yield `SEIMBANG`), account-code/category consistency, immutable used-account classification, and an expense category that names an asset account. In expense create/update service, require the debit COA type to be `expense` and prohibit debiting the payment account itself before writing either expense or journal; balancing alone misses an asset debit cancelling the cash credit. Exercise HTTP and direct-service paths in SQLite `:memory:`, run targeted and full tests, and verify live reports and journals read-only. A CSV/HTML route or Vite readiness alone is not financial sign-off, and a MariaDB ledger must not be called DB-enforced per-entry balanced merely because the application detects imbalance.
- For per-vehicle ritase history, derive the vehicle totals and paginated rows from the *same validated filtered `ritases` query* (vehicle, date range, detail status, search); include inactive vehicles in historical reads but restrict new-trip entry in both controller and service to active vehicles. Aggregate before pagination so totals do not change between pages, and sum DECIMAL strings with `BigDecimal` instead of floating-point `SUM` or PHP floats when exact Rupiah cents matter; format output from decimal strings too, since a float cast in Blade can corrupt cents. Keep sale/receipt joins one-to-one and do not add journal expenses to ritase totals a second time. Test period/status combinations, text search, pending details, inactive vehicles, pagination including a selected option matching the backend default, amounts beyond IEEE-754 cent precision, and GET array inputs in isolated SQLite `:memory:`; render a synthetic preview and inspect desktop plus mobile in a real browser. Existing table-control forms submit only their own fields, so use one unified GET form or preserve all filter parameters explicitly. A static file preview proves layout, not authenticated public navigation or mutation. For this prototype's ritase pages, keep the user's chosen bright operational-ledger style: dense legible tables and auditable numeric alignment, not decorative dashboard chrome.
- For POS workspace changes, keep the cashier task first in DOM order because CSS `order` stops applying when a breakpoint changes the parent to `display: block`. On a sufficiently tall desktop, use a two-pane workspace with Kasir fixed near 380–400px on the left and the remaining width on the right. Put a single monitoring strip at the top-right containing **Penjualan, Produk Unggulan, and Ringkasan Produk** so sales volume and stock health remain visible together; allocate width by information density rather than equally (Penjualan largest, Produk Unggulan medium, Ringkasan smallest), keep the cards equal-height, and make only an overflowing list internally scrollable. Put the wide catalog below that strip and the full-width transaction history after the workspace. On mobile, preserve the natural sequence **Kasir → monitoring cards → catalog → history**. Constrain only cart/catalog/list regions to internal scrolling, and keep product search, customer/payment controls, totals, and the review CTA inside the desktop viewport. Verify mechanically at 1440×900: Kasir width ≤400px, all monitoring-card tops and bottoms align, every card remains inside the monitoring grid, catalog begins below the strip, CTA bottom is within `innerHeight`, and history filters remain inside their full-width card. Then inspect the screenshot because page `scrollWidth` alone misses clipped controls and partially hidden list rows. At 390px assert the task sequence and no page-level horizontal overflow. In rendered-markup tests, target exact element fragments such as `<section class="dash-card sales-dashboard-card">`; a bare class token can match inline CSS before the DOM node and create a false ordering failure. Keep shorter-height and mobile layouts naturally scrollable rather than forcing fixed-height compression.
- Treat checkout as an explicit state machine: **cart → review (no POST) → final confirm (one submit) → fetch/render saved receipt → print**. Canceling review must preserve DOM and `localStorage` cart state and produce zero submissions. Guard final confirmation before native `form.submit()` so repeated pointer/keyboard actions submit once, and normalize currency fields immediately before that call. Give print a stable selector; keep it `hidden` and `disabled` by default and reset that state whenever receipt loading starts, leave it unavailable on HTTP/network/JSON failure, and enable it only after `renderReceipt()` succeeds. Pass an explicit “clear cart after success” flag for the post-checkout redirect and call `localStorage.removeItem()` only inside the successful receipt branch; an invalid receipt query must not erase the cart. Verify with a real-browser probe that spies on `HTMLFormElement.prototype.submit`, stubs delayed/success/failure receipt fetches, double-invokes confirmation, and reads back print/cart state. Rendered substring tests remain useful as a contract but never prove request counts or lifecycle behavior.
- For POS sales history, keep search, payment method, customer type, date range, and page size in one filter contract. Validate every query parameter as a scalar allowlisted value, enforce `end_date >= start_date`, and send only non-empty filters from JavaScript. Use a two-column filter grid inside the narrow side pane (one column on mobile) and verify each child rectangle remains inside the card; a page-level no-overflow check can miss a child clipped by `overflow: hidden`.
- Report runtime readback and test evidence separately from independent QC. If delegates stall or return `interrupted`, do not claim QC approval; bounded direct verification is preferable to waiting on a hung worker. Treat `hermes verify --json` according to its detected recipe: Vite build/readiness (even readiness at HTTP 404) does not run Laravel tests or prove a cashier route. Report the Laravel suite and public route/browser checks separately.
