# Kasir Bangunan prototype workflow

## When to Use

Load for changes or diagnostics in `/home/ubuntu/kasir-bangunan-app`, especially login, sidebar, and public subpath routing.

## Incumbent navigation and input workflow

- Preserve the approved green-white application shell during UI refinement: primary navigation stays in the left sidebar on desktop and becomes a left drawer on phones. Do not replace it with top tabs or a bottom menu without explicit approval; matching the palette alone does not preserve the interface.
- Master data entities must be presented as separate, directly accessible pages/sub-menus in the sidebar (e.g. Produk, Pelanggan, Supplier, Karyawan, Kendaraan/Armada) rather than bundled into a single screen with an entity-type select dropdown filter. Direct one-click access per master entity matches user workflow; never force users to pick entity types from a dropdown just to view or manage different master datasets. Land the sidebar link, panel mapping, entity dataset, form handlers, and reload/deep-link behavior as one working slice; a renamed sidebar pointing to an empty or still-combined panel is unfinished. After the direction is selected and execution authorized, continue that slice instead of repeating the same audit or asking the same navigation question.
- Present **Akun Login** as a separate Admin-only sidebar page, not part of Master Karyawan. Creating an employee record must not implicitly create a login or grant privileges. Reuse the approved list-first page and add/edit popups for name, email login, Admin/Kasir role, active status, and password changes; keep existing credentials unchanged until an explicit account action. Preserve the agreed cashier permission matrix rather than adding speculative permission toggles or new roles. Use `application-auth-security` for account lifecycle and server-enforced session revocation.
- Keep supporting CRUD/operational pages list-first, with labelled add/edit actions opening input forms in popups. The cashier is an explicit exception: preserve the approved catalogue-left/cart-right workspace, quantity steppers, visible total and checkout; stack catalogue then cart on phones. Only payment and pre-save review are popups. Never turn cashier into a nota list with an Add Sale button or put the whole sale into a long popup. Adding roles or operational modules is not permission to replace working cashier features; compare the incumbent source and flow before editing.
- For a request to match the old cashier, open the actual incumbent route and candidate in the same isolated runtime before editing. Compare the collapsed/expanded sidebar, loaded font, header/content spacing, monitoring panels, populated catalogue/cart, history, and payment/review states; copying green-white colors or only restoring two columns is insufficient. Preserve the incumbent's compact rail behavior and reuse its real components/CSS before creating replacement controls. Keep legacy source untouched when adapting the candidate to V2 data.
- Lock the measured presentation and existing flow as acceptance criteria. Capture equivalent old/new desktop/mobile states and inspect the saved image dimensions and scroll positions; distinguish restored workflow from pixel-identical appearance. For the ordered procedure, load `ui-ux-execution-standard` → `references/incumbent-preservation.md`.
- Use the reusable popup recipe in `ui-ux-execution-standard` → `references/task-workspaces.md` for DOM ancestry, named-control collisions, focus, cancellation, and request-count checks.

## Commit and Push from a Dirty Working Tree

1. Read the current branch, remote, upstream, `git status --short`, and the exact diff before staging. Treat every pre-existing modified/untracked file as user work; never use `git add -A`, `git commit -a`, or revert unrelated changes.
2. Define the authorized commit scope. Trace runtime, route, schema, view, and test dependencies; if the requested feature shares a file or migration with another domain, identify the coupling and ask which boundary to include before staging.
3. Stage only named files or exact hunks. For mixed files, use interactive staging or construct and inspect a cached patch; after staging, review both `git diff --cached --name-only` and the full `git diff --cached`. Confirm unrelated routes/hunks are absent and required dependencies are present.
4. Run the smallest relevant regression suite once in the verified isolated environment, plus `git diff --cached --check`. Do not keep repeating already-passing tests or delay the requested commit for redundant verification; add another test only when it materially closes an untested acceptance gate. When testing a clean worktree copied from a dirty Laravel repository, inspect Composer's recorded install path before execution: absolute-path autoload metadata can resolve `app/` outside the worktree, and read-only mounts can redirect Laravel logs/cache to the source tree. Use a writable disposable runtime at the expected paths, or rely only on test evidence actually produced for the committed tree; never substitute a prior dirty-tree pass as proof the clean branch passed.
5. Commit the reviewed staged set, then verify the commit hash and `git show --stat`. Check remaining `git status --short` to prove unrelated work stayed uncommitted.
6. Push only when requested. Before pushing, `git fetch origin <branch>` and inspect `git rev-list --left-right --count origin/<branch>...<branch>`. If the requested target is behind remote, do not push a stale local branch or rewrite `main`; create a task branch from the freshly fetched remote tip, port only the authorized hunks/files, inspect its full diff, verify it, then push that branch. A push does not mean merge, PR approval, deployment, or production rollout. After `git push origin <branch>`, verify the remote ref with `git ls-remote origin refs/heads/<branch>` and compare its SHA to the intended commit. Do not force-push.
7. Report commit and push separately: a local commit is not a GitHub push, and a successful push must be confirmed by reading the remote ref. Name the exact branch and SHA, state whether only the requested scope was included, and distinguish tests run on the committed clean tree from earlier tests run on a different dirty tree. Do not imply deployment from a push unless separately authorized and verified.
8. When Bagas asks whether **all changes** were pushed, answer the scope directly before doing unrelated work. Inventory tracked, modified, staged, and untracked files across the active repo and task worktrees; compare commits with `origin/<branch>`. Interpret “all changes” as current-task changes unless he explicitly authorizes a repo-wide/full-code push. For explicit full scope, include the entire local code, tests, docs, state files, and artifacts rather than silently cherry-picking a feature; still inspect candidate secrets/private data and never publish credentials. To preserve a dirty source tree and newer remote commits, fetch the target branch, export the complete local delta (including untracked files) as a binary patch from a temporary index, reset only that temporary index, apply the patch in a clean detached worktree based on the fetched remote tip, then inspect the full staged file list/diff and `git diff --cached --check`. Preserve remote ancestry; do not force-push. If the patch conflicts, stop and resolve the overlap before committing. Run the smallest relevant verification, commit the reviewed set, push only when requested, and confirm the remote ref SHA equals the intended commit. State separately what was pushed, what verification ran, and whether deployment/migrations ran.

## Pull remote code and make the deployed app use it

1. Read the active branch, upstream, `git status --short`, current `HEAD`, and remote URL; inspect the current bind mounts, deployment image/source model, and any worktree/stash state before changing Git state. Fetch the target branch and compare both sides with `git rev-list --left-right --count HEAD...origin/<branch>`; stop if local commits diverge or the intended target is ambiguous.
2. If the worktree is dirty, save the full tracked and untracked delta with `git stash push --include-untracked`, record the stash object SHA, and verify the worktree is clean before `git pull --ff-only`. Do not drop the stash. A fast-forward updates source, but restoring a pre-pull stash may conflict where newer commits touched the same files or turned formerly-untracked files into tracked files; preserve the stash and do not run `stash pop` or overwrite the pulled tip to force restoration. If apply conflicts, report the exact scope, keep the stash intact, and only clear conflicted worktree state after confirming the user's requested outcome is to run the remote code. Reapply local work later via a deliberate merge/rebase or a separate branch, not as part of the runtime update.
3. Verify `HEAD == origin/<branch>`, the worktree has no unmerged paths, and the app container sees the expected source/image. For bind mounts, compare host/container paths and read-only status, then inspect the expected changed file inside the container. For baked images, source pull alone is not deployment; follow the repo's authorized image-build/release procedure instead. Check OPcache timestamp validation and compiled-template/cache behavior before deciding whether a restart or cache clear is needed; do not restart by habit.
4. Before declaring the updated app runnable, enumerate migrations in the new commit and read the target environment's `migrate:status` plus effective database identity. Run the narrow QA suite against disposable SQLite `:memory:` first. If a production migration is needed, stop for explicit authorization, then use the private backup and invariant-snapshot procedure in `references/finance-audit-and-release.md`; run only the named migration and verify schema, seed records, business-table counts, and deterministic transaction/journal hashes afterward. Never infer that a source update is safe just because the login endpoint returns 200.
5. Clear only the relevant compiled view/cache when evidence shows it is stale and the cache operation is safe; avoid database-wide or application restarts unless required by the inspected runtime. Read back migration status and app route health. A redirect to login proves reachability only, not the authenticated feature path; label protected browser interaction as unverified unless actually exercised.
6. Report separately: pulled commit, runtime code source, migrations applied or pending, tests and HTTP results, whether a restart/build happened, authenticated UI coverage, and the exact stash SHA for preserved local work. Never imply pull equals deployment or deployment equals verified functionality.

## Shared CRUD Forms and Themed Date Pickers

1. Treat screenshot diagnosis as a hypothesis, not proof, because existing flex centering may already be correct. Scope styling to explicit form classes or `.form-group` descendants; exclude hidden, checkbox, and radio inputs from text-field rules. Find duplicate selectors and later media rules first, because the last matching `grid-2` rule wins and can silently undo a new shared layout.
3. Preserve each form's action, method, CSRF/method spoofing, names/IDs, validation semantics, and data attributes. Do not add controls that imply unsupported controller behavior; form polish is not permission to change persistence or filters.
4. Keep a native date input as the canonical successful form control (`name`, `id`, ISO `YYYY-MM-DD`, `min`, `max`, `required`, `disabled`) when adding a themed calendar. Synchronize selected dates to `.value` and dispatch native `input`/`change` events so inline handlers and existing JS consumers continue to work. Do not suppress the native picker until the custom control has initialized; retain a native fallback when JavaScript is unavailable or fails.
5. Implement the custom calendar against the WAI-ARIA APG dialog/grid pattern: labelled month/year live region, one roving tab stop in the day grid, arrow-key day/week movement, Home/End week movement, PageUp/PageDown month navigation (Shift for year), Enter/Space selection, Escape close, outside-click close, and focus restoration.
