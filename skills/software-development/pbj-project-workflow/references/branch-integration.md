# Collaborator-branch comparison and selective integration

Use when reviewing incoming PBJ changes against a locally hardened, possibly dirty worktree. Preserve the owner's stated conflict priority; do not convert audit permission into a merge or runtime migration.

## 1. Freeze the versions and protect local work

1. In the verified repository, run `git status --short --branch`, `git remote -v`, and `git fetch origin --prune`. Discover exact ref spelling before selecting it.
2. Pin `git rev-parse HEAD origin/<branch>` and `git merge-base HEAD origin/<branch>`. Use these fixed object IDs throughout the review so a moving remote cannot silently change the target.
3. Enumerate local tracked changes with `git diff --name-only` and relevant untracked source with `git ls-files --others --exclude-standard`. Save a private source snapshot plus SHA-256 manifest outside the repository. Include tests, routes, views and services; exclude secrets, sessions and runtime storage.
4. Enumerate incoming files with `git diff --name-status <base> <incoming>`. Record separately: incoming changes, files changed on both sides, and actual text conflicts. Do not infer conflict count from the number of overlapping filenames.
5. When reopening a collaborator review, also pin the previously reviewed incoming commit. Run `git log --oneline <reviewed-incoming>..<latest-incoming>` and `git diff --name-status <reviewed-incoming> <latest-incoming>` before reusing an old verdict. Distinguish an older deliberately held hunk from a newly added change; a stale audit cannot explain why a later independent copy change is absent.

## 2. Simulate without touching the worktree

For each incoming path, export `git show <base>:<path>` and `git show <incoming>:<path>` to a private scratch directory, and copy the ACTUAL working file as the local side. Treat an absent base or new file explicitly rather than mistaking an expected missing path for a failed audit.

Run `git merge-file -p <ours-snapshot> <base-snapshot> <incoming-snapshot>` and save its stdout as a preview, never as the live file. Interpret positive conflict results separately from command errors. Do not use checkout/reset/stash or blanket `-X ours` to manufacture a clean workspace: those operations can hide or discard the very changes the owner prioritized.

Inspect semantic conflicts even when text merges cleanly: middleware exemptions, posting dates, reversal ownership, historical filtering and schema prerequisites can change behavior on distant lines.

## 3. Assign bounded audit ownership

Split independent concerns into small principal-file scopes, typically three files: financial lifecycle, driver/master schema, or shipment/form payloads. Give each worker the pinned refs, current-worktree priority, no-write boundaries and an exact report path. Dependencies may be read, but do not let two workers own the same edits. Keep a financial QC reviewer separate from implementation.

The parent owns aggregation, conflict decisions and serialized disposable tests. Worker reports are hypotheses until checked against the pinned code and real execution. If a completed worker times out without a final summary, inspect its declared output paths once before repeating the work: a saved report may be complete, but independently recompute hashes, trace the actual routes, and verify the claimed diff boundaries before accepting any finding. Record the timeout separately from the verified artifact; neither timeout nor a saved PASS determines the verdict. Reuse validated artifacts to finish aggregation instead of restarting the entire audit. Do not claim all incoming files were reviewed merely because a few scopes or probes passed.

## 4. Probe dangerous behavior before adoption

- Inspect helpers named `has*`, `memiliki*`, scopes and page-load synchronizers for DDL/DML before treating them as reads. On disposable target MySQL, call the real helper and compare schema nullability, columns and source rows before/after; record executed ALTER statements. Keep schema changes in explicit migrations, not hidden in page visits.
- Trace migration calls into application models. A migration invoking a mutable synchronizer may rename IDs, reclassify employees or clear document links instead of merely adding schema. Reject hard-coded legacy-code transformations and silent exception swallowing from automatic adoption; require approved mappings, atomicity, preserved evidence and separate rehearsal.
- Preserve historical employee receivables, payroll and ritase when introducing internal/partner categories. Current ownership filters must not make already-posted debt or evidence disappear. Never infer ownership solely from an old code or matching name.
- Audit route additions together with every global-middleware exemption. Drive anonymous HTTP requests through the real kernel and check the exact schema column names. A 500 after an authentication bypass is not a successful authorization rejection, but also does not establish successful data disclosure when the query failed. Report those findings separately.
- Treat foreign-key disabling and broad relationship rewrites as integrity risks, not proof of a safe identity migration. Check every referencing domain and historical audit/source reference before considering a mapping.

Use only guarded disposable databases and frozen source snapshots for mutating probes. Keep live runtime, historical data and credentials outside the review.

## 5. Adopt selectively and prove preservation

Classify each change as retain-local, adapt, safe-to-adopt, owner-decision, or unverified. Apply only a bounded approved adaptation with a failing reproduction and a distinct hardening pass; do not import unrelated migrations or debug endpoints along with useful UI work.

Before accepting delegated implementation, inspect the current worktree yourself: `git diff` omits untracked migrations and tests, so enumerate `git status --short` and open every untracked source file as well as the tracked diff. Run `git diff --check` for tracked edits, then separately lint or inspect new files. Treat PHP lint and model-shape assertions (`getFillable()`, `method_exists()`) as syntax/structure checks only—not proof that validation, persistence, migration, edit-preservation, or Blade behavior works. Make acceptance tests drive the real controller/model/schema boundary in a guarded disposable environment, and assert the required before/after state; for a new rule, demonstrate the check rejects a deliberately missing/disabled rule when feasible. Trace Eloquent relationship signatures and every field synchronized to a second table against that table's actual schema: valid PHP syntax can still hide wrong relationship keys or duplicate/nonexistent columns.

Audit the integration boundary separately from each file's internal correctness. For a new Blade partial, trace the host view's option variables, controller `compact` payload, Alpine state/watchers/handlers and canonical hidden form fields. A partial can pass scoped QC and still break its host because its companion files are missing. Do not hide the dependency by supplying empty arrays that make partner selection unusable. Freeze the compatible companion set, exercise actual render, dropdown interaction and submit/readback on disposable data, then adopt the set together. A dependency-free refinement may ship separately only when its exact source and behavior are independently verified.

Recheck the protected-file manifest after read-only auditing. After intentional edits, review exact diffs, rerun affected and combined financial tests, then check role enforcement, browser payloads, exports and visual evidence where relevant. Verify packaged code matches the tested hashes.

Consolidate business impact, evidence limits and adoption decisions in the existing readable PBJ status document. Distinguish reviewed, reproduced, corrected, integrated and deployed; a successful probe proving a defect is not a completed correction.

### Audit missing collaborator UI without blanket rejection

1. Translate the report into named user-visible surfaces before assigning scopes: the role's page, sidebar category destinations, dispatcher queue/banner/button copy, and each requested print document. Keep material and semen print variants separate. Divide independent view groups among bounded reviewers; keep the parent responsible for one consolidated adoption inventory rather than repeated assurances.
2. Compare each surface across latest incoming, previously reviewed incoming, current working source and a read-only snapshot of the running container. Use `git show <ref>:<path>` for incoming source and `docker cp <app>:/var/www/html/<view-path> <private-snapshot>` for runtime. Record real hashes and inspect the semantic diff; file inequality alone neither proves an entire feature is missing nor establishes a regression. Recompute hashes in child reports instead of trusting plausible-looking digest strings.
3. Classify changes by mechanism: text-only, styling-only, shared toolbar/component extraction, data-contract change, authorization change, or financial/status behavior. Inspect each hunk's required variables, handlers, includes and routes. A queue title or button label can be independent of an unsafe assignment controller; retain the backend hold without automatically withholding the safe presentation change. Assert a color mismatch only when the compared classes/styles actually differ.
4. Distinguish sidebar shortcuts from in-page category tabs and from backend classification support. Inventory the actual labels, named routes and `tab` query values rather than saying all driver/vehicle work is either present or absent. If category shortcuts are requested, assess adapting them to the existing `.link-sidebar-subitem` conventions, direct-link parent and SPA synchronization without overwriting protected report navigation or RBAC. Treat duplication as a UX decision, not a demonstrated financial or security defect.
5. Resolve each SPP/SPJ/SPBG named route to its controller method and returned view before comparing print files. A document can be rendered under another domain's directory, and different endpoints with the same document label may enforce different roles. Inspect both the screen toolbar and printed sheet: a new shared toolbar include can explain a missing UI update even when the document body is unchanged. Check its variables, print-hidden behavior, copy/recipient modes and companion handlers before proposing adoption; preserve approval and document-data gates. Compare toolbar availability with the full controller gate, including approval identity rather than status alone. Preserve individual recipient-copy selectors unless their removal is approved; an unchanged document body does not prove all copies remain separately reachable. Treat a request/query role label as untrusted presentation input, never authenticated authorization. A source-only toolbar audit cannot establish zero risk or rendered print quality. Generate acceptance PDFs under explicit `page.emulateMedia({media: 'print'})`, restoring screen media afterward: a previous screen-media override can keep toolbars visible and change pagination even when `page.pdf()` succeeds. Verify the actual PDF text, recipient labels, page count and footer placement; preserve document data while correcting only a reproduced overflow. After refreshing Blade files in a long-running disposable CLI server, check the served response for the changed marker, not only the copied file hash; clear that clone's compiled views and restart only its inspected HTTP process if it still serves stale output, never the active application's container.
6. Report preserved local corrections as such. A hardened driver template may intentionally retain partner identity/documents, initialized status options or reachable mobile modals instead of matching incoming bytes. Do not overwrite those fixes merely to make hashes equal, and do not portray intentional style adaptation as proof that a requested submenu or toolbar already exists.
7. Read old audit decisions at their evidenced scope. A reproduced internal-cost/ritase field allocation error on synthetic data is not proof that real money was disbursed. A whole-layout merge that would regress reports is not proof that carefully adapted sublinks are unsafe. Separate confirmed behavior, potential impact and UX preference; do not attribute malicious intent to a contributor's older branch base.
8. Deliver a concise per-surface result: what differs on the running application, whether it is newly incoming or previously held, the exact dependency boundary, and what remains unverified. State source-only comparison versus rendered/browser/printed evidence explicitly. A forwarded colleague or agent report permits verification, not an automatic merge, redesign or deployment. After implementation is authorized, exercise the adapted navigation and print output in isolation and apply the existing publication gates; do not present that unexecuted step as already validated.

## 6. Publish only the approved branch slice

1. Fetch the target branch and compare local/remote ancestry before staging. Do not resolve remote drift with an automatic rebase, merge or force push on a dirty collaborator workspace.
2. Build an explicit manifest of selected app, route, view, migration, test and documentation files. Inspect selected files for mixed ownership: a shared test runner can contain older, unrelated changes even when its filename belongs to the requested feature. Reconstruct that file from the pinned Git base with only the approved feature changes in a separate candidate tree; preserve the full working copy. Leave quarantined candidates and their exploratory RED-only scenarios outside the release. Preserve those scenarios privately rather than weakening or deleting the material assertions that already pass.
3. Audit release notes and run commands against the selected tree. Tell readers to use the disposable env-gated runner; a bare fixture command can otherwise bootstrap an active application's database. Describe migrations as rehearsed, not live-applied.
4. Re-run the affected and combined suites against the exact candidate tree. When extracting a passing subset from exploratory work, verify the retained branches are unchanged and execute the release subset again. Compare all tracked candidate entries against the pinned base, not only the selected paths: for Git mode `120000`, compare the symlink target text (`os.readlink`), not the bytes of its resolved file. This prevents a preserved schema symlink from being misclassified as an unauthorized schema edit. Inspect build-induced lockfile changes separately; if tooling changed only the root package name to the scratch-directory name, restore that field to the pinned value and run one build with the restored lock. Do not import incidental lockfile or dependency changes into an unrelated release.
5. Stage explicit paths, then inspect `git diff --cached --name-only` and `git diff --cached --check`. A failed `git add` may already have staged other arguments, so inspect the index before retrying. Normalize whitespace without changing semantics; preserve Markdown hard breaks explicitly. Do not force-add ignored logs broadly: only include exact, scrubbed synthetic evidence files when the release needs them.
6. Compare index blobs to the manifest, check reviewed hashes remain current, and commit only the selected set. If whitespace normalization changes an audited hash, record that difference instead of claiming byte-identical QC.
7. Push with an explicit destination such as `git push origin HEAD:refs/heads/sandbox`, without force. When promoting a candidate branch to `main` while currently on a dirty `sandbox` worktree, do NOT switch branches: update the local branch ref via `git branch -f main <candidate-ref>`, execute a dry-run check `git push --dry-run origin main:refs/heads/main`, push via explicit refspec `git push origin main:refs/heads/main`, and read back `git ls-remote --heads origin main` to confirm SHA parity. When `main` is excluded, compare its remote SHA before/after as well. Verify the committed file set and blob hashes against the staged manifest, and confirm unrelated working-file bytes remain intact. Finish with one short report containing branch, commit link, verified tests and unchanged surfaces. A subsequent build-only notification is not a substitute for that completion report. Keep test execution, Git publication and runtime deployment distinct; do not call absent remote checks a green CI run.

## 7. Assess migration safety before an approved release

### Final destination: company Git main and VPS

Treat the PBJ sandbox as a validation stage; the owner's intended deliverable is reproducible code that can enter GitHub `main` and run on the real company VPS. Design every accepted correction for that transfer, not just for the currently hot-patched sandbox. A clarification of this final destination is not immediate permission to push `main`, access the destination, or cut over production. Keep those authorizations explicit.

Bind production readiness to the exact complete Git release tree and the destination's inspected PHP/MySQL version, configuration, existing schema and pending migrations. Latest UI tests on a MariaDB runtime clone do not establish acceptance on company MySQL, and older MySQL backend tests do not automatically cover newly changed views. Rehearse the exact Git package as an upgrade on an isolated target-version restore; preserve application keys, environment configuration, account identities, historical business values and uploaded files. Do not require a clean installation, demo seed, database reset or engine change to make an upgrade pass. Record sandbox testing, Git promotion and company cutover separately, including a tested database/upload restore and post-cutover version verification.

1. Enumerate the target database's migration history and ENTIRE pending set read-only before recommending execution. Laravel `php artisan migrate` applies every pending file, not merely the new driver migration; historical cleanup or identity-renumber migrations can rewrite live data. Do not mark old migrations applied just to skip their effects.
2. Compare the target's actual column lengths, nullability, defaults, indexes and engine/version with the rehearsed schema. A nullable `change()` that also fixes a varchar length can narrow a divergent schema; an additive design does not promise zero ALTER TABLE blocking.
3. Rehearse the pending upgrade on a representative isolated copy of the target version, verifying existing IDs, document links, role references and financial rows before/after. Distinguish a fresh install, rerun and real prior-version upgrade.
4. State irreversible `down()` behavior before deployment and verify a logical backup restore or forward-fix recovery path. A code `git revert` does not undo schema changes, and an intentionally rejected `migrate:rollback` is not a completed recovery plan.
5. Report separately: what the migration changes, what preservation was exercised, and what remains unverified on the VPS. A push never establishes that a migration ran or that the live database is safe to migrate.
6. Hardening deployment & rollback scripts (`deploy.sh` & `rollback.sh`): Never rely on a bare `git pull && docker compose up -d && php artisan migrate` as a production gate.
   - Fail-closed backup: The script must execute an automated timestamped logical backup (`mysqldump` compressed to `backups/deploy/`) before touching code or containers. If the `db` service is not active, bring it up, await healthy status, verify the dump file size (>1KB) and validate archive integrity with `gzip -t`. Never skip backup; abort immediately on backup failure.
   - Migration sequencing & container runner: When container startup (`entrypoint.sh`) gates boot on pending migrations (`migrate:status --pending`) to prevent crash-loop uncoordinated mutations, running `docker compose up -d` before migrating will cause the app container to abort startup on pending migrations. The deploy script must execute migrations via a one-off runner container (`docker compose run --rm app php artisan migrate --force`) *before* starting daemonized services (`docker compose up -d`).
   - Rollback precedence: In `rollback.sh`, verify backup integrity and restore the database *before* reverting code or rebuilding containers. If database restoration fails or an unsupported engine collation is detected, trigger an immediate `CRITICAL HOLD` and keep the application in maintenance mode (`artisan down`) to prevent data corruption.
   - HTTP health check: Require HTTP 200/302 from the local web endpoint before declaring success.
   - CSRF testing caveat: In Laravel, `ValidateCsrfToken` bypasses verification when `runningUnitTests()` is true (`APP_ENV=testing`). Missing-token/CSRF rejection checks (asserting 419) must run under `APP_ENV=production` or an explicit non-testing session harness.
   - Scrubbing release trees: Untrack legacy internal spreadsheets, spreadsheets in `public/exports/`, and demo seeds from the Git candidate tree before promoting to `main`; do not rely solely on `.dockerignore` to hide sensitive files that remain in repository history.

### Keep fresh installations clean without erasing existing records

1. Trace the deployed startup path before attributing inserted rows to Git: inspect the entrypoint, migration `up()` bodies, baseline dump and automatically invoked seeders. A push or pull moves source; a subsequent migration/startup hook is what can write the database.
2. Classify each inserted row set as fictional example data, required reference data, or an approved conversion of existing history. Remove only the unwanted example insertion from the fresh-install path and keep demonstration seeders explicitly opt-in; deleting every migration `insert` can break reference accounts or historical upgrades.
3. Test a fresh disposable installation and a no-op rerun. Assert that the unwanted master rows remain absent, schema and required references exist, and already-populated legitimate records remain unchanged. Bind the result to the edited source rather than to a container still running the old migration file.
4. Treat existing-row cleanup as a separate action: editing a migration already recorded as applied does not remove rows. Establish the exact target database, take a recoverable backup, and check references across transactions, shipments, buyer defaults and free-text source-name snapshots—not only declared foreign keys.
5. Do not infer that production is empty from sandbox counts. If cleanup is authorized, select the exact unwanted records using multiple identifying fields and preserve changed or referenced rows for review. Avoid `TRUNCATE`: it erases every row, resets identity state and is not protected by a normal transactional rollback on MySQL.
6. Read back the exact target after cleanup and report source prevention, sandbox cleanup and destination-VPS cleanup separately. Do not run an existing migration's `down()` merely to recreate an empty master table; it can drop legitimate data.

## 8. Preflight a public-sandbox runtime publication

1. Resolve the requested surface before changing it: Git branch, public sandbox web, or destination VPS. Understand the user's boundary: 'main' explicitly refers to the destination VPS / production server, while 'sandbox' (the public test application at jajandigital.web.id/pbj) is the designated deployment target for verified features and collaborator adoptions. Do not confuse protection of the destination VPS with refusing or withholding deployment to the sandbox web. When adoptions (such as driver partner/KSO classification, financial guards, or super admin controls) are verified, publish them to the sandbox container environment after taking backups and applying necessary schema migrations, keeping only the destination VPS strictly untouched. Treat a publish request as permission for the named surface, not authorization to change its database engine, accounting policy or historical records.
2. Use `terminal` in the verified repository to inspect `docker ps`, then parse `docker inspect` through a field whitelist: image ID, command/entrypoint, state/health, mounts, ports and Compose labels. Do not print the full inspect object or expanded Compose configuration, which can expose environment secrets. Use `read_file` for the repository Dockerfile, Compose file and entrypoint, and compare them with the running source rather than assuming the repository describes the live deployment.
3. Establish the live engine/version and schema read-only. Inspect application boot providers before bootstrapping a read-only Laravel query, because boot hooks can themselves perform DDL/DML. Compare applied migration names with the entire workspace migration set and inspect required columns. Verify actual column types and allowed statuses even when migration history says the change ran: an already-recorded migration can coexist with an older enum that rejects the application's warehouse-loading status. Reproduce this on a restored copy, then add a narrowly scoped forward migration; do not rewrite applied history or mark a missing change as already satisfied.
4. Trace startup side effects before building, restarting or recreating a service. If app startup executes `php artisan migrate --force`, require approval for the identified pending set, a restored backup and upgrade rehearsal on the actual target engine/version before allowing startup. Do not bypass approval by restarting the old container, marking migrations applied, inventing an untested startup switch, or changing the database service to match Compose.
5. Freeze the compatible source set only after implementation owners and QC finish. Compare three distinct baselines: the pinned Git tree, the tested worktree, and actual source copied from the running container. For a Git package, use `git archive <commit>` plus only the approved changes. For a runtime package, preserve existing live hotfixes and overlay only the approved change onto the inspected running-source baseline; replacing it with Git HEAD can regress unrelated behavior. Record both manifests and test both packages when they differ. Keep secrets, runtime storage, sessions, held candidates and unrelated untracked artifacts outside build contexts. If reusing the inspected runtime image as a dependency-preserving base, compare `composer.json` and `composer.lock` against the selected source; inspect frontend source and package locks separately before building CSS, because the live frontend may differ from Git. Tag the verified local image ID before using the tag in Dockerfile `FROM`; a bare `sha256:` image ID is not a registry repository reference. Build an immutable candidate, extract its source with `docker create` plus `docker cp`, and compare it to the manifest. Rehearse its backend and browser flows against an isolated restore of the actual target engine/version with an inert entrypoint and no migrations when none are required. A built image or successful rehearsal is not a live cutover; report the publication method and exact served hashes only after the external write and readback occur.
6. Preserve rollback from the running containers, not mutable image tags: obtain each exact image ID with `docker inspect --format '{{.Image}}' <container>` and tag that ID with `docker tag <image-id> <rollback-tag>`. Record the actual command, entrypoint, mounts, networks and healthcheck; recreating from a divergent workspace Compose file can change more than the image. Preserve any authorized source hotfixes made inside the current containers, because those files may differ from the underlying rollback image. Identify separately which public assets or documents are volume-backed; retagging an image does not restore a changed volume or undo a database migration.
7. After an authorized release, verify app/worker image identities, health, exact source hashes and public HTTP response, then perform authorized authenticated smoke checks. State separately what was published, whether schema changed, and which workflow checks remain unverified. Do not substitute login availability for financial acceptance. Bound preservation claims to the actual before/after evidence: matching row counts do not prove unchanged historical values, and no active TCP connection or unchanged SSH known_hosts does not prove a server was never accessed. Report which commands and targets this release actually used rather than declaring the destination VPS universally 'sterile'.
8. For an explicitly authorized code-only sandbox slice with pending unrelated migrations, rehearse scoped publication against a restored clone of the actual engine/version before considering in-place copies plus PHP-FPM USR2 reload. A signal reload does not run the container entrypoint; a restart does. When `entrypoint.sh` executes migrations automatically on startup, container restarts must be avoided. Execute in-place copy strictly via:
   - Pre-copy backup of live container files to host cache.
   - `docker cp <file> pbj_app:/var/www/html/<target>` followed by `chown www-data:www-data`.
   - Purge compiled views via `php artisan view:clear`.
   - Send `kill -USR2 1` to reload FPM master worker processes without downtime (required when `opcache.validate_timestamps=0`).
   - Validate post-copy hashes using `sha256sum` inside the container.
   Preserve actual runtime source divergences in the recovery/release image, freeze the application/worker write window, compare business-table digests, and read back both source and public-asset hashes. Docker exec cannot run while a container is paused; use docker cp for paused-worker file readback or resume only after the comparison window. Keep the reported method honest: a prepared image and an in-place source publication are not an image/container cutover.
9. Probe internal Nginx using its real root route (for example `/login`) and the public proxy with its prefix (`/pbj/login`); a wrong internal prefix can falsely trigger rollback after a successful update. Bound health probes with connection/total timeouts and a finite retry budget, treating a transient nonzero curl exit as a failed attempt rather than throwing before the retry loop can run. Roll back on persistent failure, then read back exact source/assets and service availability before any retry. If the public origin has no saved vault login and the headless UI cannot prompt, retain authentication, do not manufacture sessions or seed live users, and disclose that public authenticated interaction remains unverified despite a passing isolated full workflow.
10. When a shared runner mixes approved and held work, construct the release runner from the pinned Git base and overlay only approved hunks in a separate candidate tree. Execute the candidate, then stage its exact tested blob with `git hash-object -w` and `git update-index --cacheinfo`, leaving the full working file intact. Verify all index blobs and unrelated dirty-file hashes before commit; never replace the working runner merely to make staging easy.

### Rehearse a stateful upgrade against the target version

1. Create a restricted logical backup using the credentials resolved inside the target container, never printed in the transcript. Restore into a separate database container running the exact inspected engine image, on an internal network with no published database port or live data-volume attachment. Retain backups outside temporary directories when they are needed for recovery.
2. Start the candidate image with an explicit inert entrypoint for inspection, so normal startup cannot migrate before the before-state is recorded. Use an isolated database name/configuration and inspect any bootstrap hooks before treating a query as read-only.
3. Capture schema, row counts and a deterministic digest for each existing table. Canonicalize row representations and sort them before hashing; record the old column set so newly added default columns do not falsely appear to change historical values. Keep raw rows private. Declare expected changes to migration history or reference-role rows explicitly rather than exempting all master data.
4. Apply the exact expected pending set, compare old-column digests and counts, assert no unexpected table/value changes, then rerun migrations and require a no-op. Inspect the actual expanded schema as well as migration names. Exercise the candidate's real cache commands and startup/readiness behavior against that restored copy.
5. Run mutating regression fixtures in a separate guarded test schema on the same isolated server, not in the preserved upgrade copy. Require suite-specific final markers and exit status. Keep preservation evidence distinct from synthetic business-test results: matching historical hashes prove preservation, not correctness of the imported accounting balances.
6. Bind backup restoration, upgrade, source parity, business tests and QC to the immutable candidate identity. If a later schema correction or source edit changes that identity, repeat the affected gates and refresh the manifest rather than presenting earlier image results as final.

This rehearsal recipe does not establish that a live cutover occurred; runtime publication still requires the step-7 readback.
