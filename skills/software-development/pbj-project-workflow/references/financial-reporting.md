# PBJ financial-reporting audit and delivery gates

1. Read routes, reporting controller, views, journal service, and all posting callers before proposing calculations. Compare workspace controller to deployed runtime before claiming a finding applies to the sandbox. Record which statements are code facts versus unverified transaction-level risks.
2. Establish the effective date and treatment of opening balances; compare journal mutations to operational sources including cancellations, reversals, deposits, returns, and backdates. Require an explicit cutoff convention before historical reports. When comparing `saldo_berjalan` against `saldo_awal` plus signed journal mutations, report mismatched accounts as reconciliation exceptions, not proven misstatement: imported/seeded balances and missing history can produce the same observation. Compute the signed mutation with a subquery that joins `jurnal_umum` to `data_kode_akun`: the normal side (`saldo_normal`) lives on `data_kode_akun`, so referencing it inside a `jurnal_umum`-only subquery fails with `Unknown column 'saldo_normal'`. Then split the mismatches instead of treating them as one class — an account whose `saldo_awal` AND signed mutation are both zero while `saldo_berjalan` is nonzero was written by a seeder/import setting running balances directly, so investigate it as data provenance, not as a defective posting writer. Whole-table tells of the same: journal row count far below account count, and every journal date on a single day. Report both classes separately and never restate the total difference as a rupiah misstatement. Before interpreting ANY per-account difference, test whether the fixture's opening balances balance at all: sum `saldo_awal` separately for `saldo_normal = 'Debit'` and `'Kredit'` accounts and compare the two totals (do the same for `saldo_berjalan`). When the seeded opening balances are themselves unbalanced by a material amount, no account-level difference can be read as a misstatement measure — report the fixture imbalance as the finding and stop, because every downstream comparison inherits it. Specifically flag opening balances in nominal/expense accounts (e.g. `506% Beban Penyusutan`) for provenance review against dated source records and any prior closing entries; neither the correct destination account nor the cause of a baseline imbalance can be inferred from the account name or the residual arithmetic alone. Also list accounts whose cached balance sits on the wrong side (negative on a debit-normal account): that is a legitimate value to display, not a defect to hide.
3. Trace all direct journal writers/deleters and page-load synchronizers before trusting the journal as immutable; a GET that syncs spareparts can mutate ledger data — remove all `sinkronkan*` from `index()` GET and expose it only as an explicit POST (e.g. `keuangan.akuntansi.jurnal.sinkron_sparepart` guarded to SPV_KEUANGAN via a manual button). On reversal, test both journal rows and cached COA balances: inserting an opposite entry without applying its delta atomically leaves cached balances stale. Lock original entries inside the reversal transaction so simultaneous cancellation cannot create duplicate reversals. After a reversal, the posting service's idempotency guard must match only journals that are still active (or NULL status on legacy rows): a guard that matches any row carrying the reference makes a cancelled reference impossible to re-post, so a corrected re-post silently returns the dead journal number instead of writing a new entry. Test post → reverse → re-post the same reference, not just post → reverse. Route every multi-row cancellation through ONE shared helper that selects the active journal numbers for a reference under `lockForUpdate` and reverses each, rather than repeating the select-and-loop at each caller. Before any existing PRT-* journal changes nominal or transaction date, reject changes touching a closed period (check both old and new dates), then prefer reversing and reposting through the shared journal service so the historical row stays traceable; if an approved transitional path still updates in place, require one transaction spanning the operational source edit and journal sync, period-row locks for both old and new dates, locked source/journal/COA rows, signed delta to `saldo_berjalan`, and an isolated test proving rollback and closed-period behavior. Let sync errors propagate rather than logging and returning success; a caught error after source commit leaves stock, source, and journal inconsistent. Reject a transition to zero while an active journal exists unless it is explicitly reversed, and constrain updates to active rows so prior reversal evidence is never modified. A standalone `lockForUpdate()` query outside a transaction does not protect the following update. Orphan PRT-* rows must be reversed through the shared service, never `DELETE`. Keep existing historical rows untouched; test a fresh post/reversal and duplicate-reversal rejection on disposable target MySQL. Enumerate every direct `jurnal_umum` delete site before editing any of them and classify each one by what it does to cached balances, then re-classify by whether the rows it touches can already be reversed. A site that computes the per-account delta and `increment('saldo_berjalan')` before deleting looks correct and is correct only while every row it reads is still active — because it reads ALL rows carrying the reference, including rows already marked `dibalik`, it re-restores balances that `balikJurnal` already restored, so cancelling a slip whose journal was reversed earlier moves the balance twice. Manual-delta-plus-delete is therefore NOT safe by construction: route these sites through the shared reversal helper too, and prove it with a post → reverse → cancel-sequence test asserting the balance is unchanged by the second operation. Convert the sites that delete rows without restoring cached balances (ritase accrual update and destroy, SPK sparepart deletion). For bulk synchronizers, skip orphan `PRT-*` rows instead of deleting them, and reverse a single orphan through the explicit POST path so the balance flip stays transactional. When the audit is done, re-grep for direct `jurnal_umum` writes and require the only remaining hits to be inside the journal service.
4. Use the journal as the statement source and operational tables as subledgers to reconcile. Trial balance checks opening + debits − credits against closing (respect normal side); reconcile bank, receivables/payables, inventory, and asset register to COA. Show unexplained differences, never a balancing plug.
5. P&L: compare revenue categories, discounts/returns, HPP at sale (not purchase), depreciation expense and operating expense by identical periods; preserve losses as negative. Tax estimates require approved policy and applicable law, not an assumed flat rate: remove hardcoded flat percentages (e.g., 11%) from controllers and Blade views, present operating profit as the journal-derived figure pending tax verification, and recognize tax expenses only when backed by posted tax journal entries with clear memo disclosure. Trace every view tab, summary badge, print view, trend label, and CSV export for stale claims of after-tax profit, healthy margins, or completed reconciliation; changing the central table alone leaves misleading claims elsewhere. Do not expose a hardcoded zero as `bebanPajakRiil` or a duplicate `labaBersihSetelahPajak` while tax is unknown, because even hidden controller fields can be reused as apparent facts. Render the real Blade with controller data and assert both required disclosure and absence of unverified claims; compare every screen/print total and label against the CSV's final row, not merely its tax disclosure. CSV must use actual newline separators and quote fields so commas in values do not shift columns. Grep the reporting controller for prefix predicates (`like '101%'`, `like '506%'`) before trusting any grouped total: a code-range predicate silently absorbs whatever accounts fall in that range, pulling restricted-fund accounts into cash and depreciation EXPENSE accounts into accumulated depreciation, and no test of the report's arithmetic will reveal it. Confirm each revenue and expense account is referenced by explicit code rather than assumed covered by a category — an account present in the COA can be missing from every report query.
6. Balance sheet: gross assets, credit-normal accumulated depreciation, liabilities, contributed capital, dated retained earnings and current result. Watch for double recognition after closing entries and accidental inclusion of depreciation expense in accumulated depreciation. Calculate balance sheet cutoff per end of selected month (`Y-m-t`) from `saldo_awal + mutasi jurnal aktif`: querying real-time `saldo_berjalan` leaks subsequent months into earlier balance sheets. When a statement helper filters journal rows by `status_jurnal`, drop that filter: excluding non-active rows removes the ORIGINAL journal from its own period while its reversal lands in a different period, so a reversal dated in a later month makes the earlier period lose the transaction entirely. Count every journal row by its own `tanggal_transaksi` — the original stays in its period and the reversal subtracts in the period it was posted — and prove it with a cross-month reversal test asserting the earlier period's figure is unchanged and the later period nets to zero. Period membership and reversal treatment are separate concerns: filtering on status is not a substitute for dating. Also check that every view rendering these totals reads the helper's dated field (`saldo_cutoff`) rather than the stale `saldo_berjalan` column, or the page silently mixes dated and real-time figures. For accumulated depreciation, strictly filter for `kelompok_akun = 'Akumulasi Penyusutan'` or credit-normal `202%` accounts and strip fallback reads to operational tables (`riwayat_penyusutan`). Preserve the signed contra-asset balance and signed net asset value: `abs()` on abnormal debit balances and `max(0, gross − contra)` mask exceptions. Show the abnormal sign and warning in the rendered balance sheet; test both a debit-sided contra-asset and negative net asset on disposable MySQL. Replace a removed fallback with a visible reconciliation panel comparing the COA total against the operational register (asset register, subledger) and showing the difference as an open reconciliation item — deleting a silent fallback without surfacing the gap just hides the discrepancy in a different place. For contributed capital and retained earnings, sum the real COA accounts (`tipe_akun = 'Modal'`) plus accumulated revenue minus accumulated expense to the cutoff, so equity reflects real balances and any imbalance surfaces in the view's discrepancy banner (`$selisihNeraca`). In P&L, aggregate revenue (`Pendapatan`) from journal credit mutations within the selected calendar month and verify all active revenue accounts (such as `40404 Pendapatan Penjualan Material Alam`) are mapped rather than dropped; calculate HPP (`Harga Pokok Penjualan`) and operating expenses (`Beban Operasional`) from journal debit mutations within that same date range instead of using `max()` against operational tables or falling back to un-dated running balances.
7. Cash flow: enumerate actual cash-equivalent accounts; classify dated cash movements into operating, investing and financing; remove internal transfers; distinguish credit sales/purchases from receipts/payments and deposit receipts from deposit utilization. Reconcile beginning cash + movement = ending cash. Eliminating internal transfers means removing them from the GROSS inflow and outflow lines, not merely letting them net to zero: a transfer between two cash accounts shows as matching debit and credit, so the net figure looks correct while both gross lines inflate and every ratio built on them is wrong. Detect a transfer as a journal whose every line posts to a cash account and exclude the whole journal number from the gross aggregates, leaving ending cash untouched. For a revenue line, check how the posting service writes it before subtracting a discount again: when the journal credits the revenue account with the NETTO amount, subtracting the invoice discount from a journal-derived revenue total double-counts it — surface the discount as a memo line labelled as already included, and assert revenue equals the sum of journal credits. Beginning cash comes from the position BEFORE the period, not from ending cash minus a movement figure. Map cash movements to Operating, Investing, or Financing only after checking every counterpart row (`barisLawan`), the source document, and the approved cash-account definition; a `202%` prefix can also contain contra-assets, and a mixed journal cannot safely be assigned by the first matching counterpart. Keep unknown or mixed transactions in an explicit Unclassified bucket rather than defaulting all others to Operating. Classify a journal with multiple distinct counterpart accounts as unknown until source evidence supports a split; do not automatically promote it merely because every counterpart shares an account category, since their allocation and source may differ. A first-match asset account can silently label the entire cash movement as investing. Treat a direct cash/HPP counterpart as unclassified pending its source document (HPP recognition is usually noncash); distinguish bank principal liability from supplier liability before assigning financing versus operating. Guard an empty approved cash-account list before generating `IN (?, ...)`, and render an explicit 'account mapping unavailable' warning rather than interpreting calculated zero as actual cash. Assert the unclassified amount appears in the rendered page as well as the controller, and label still-heuristic operating/investing/financing totals provisional. Verify Operating + Investing + Financing + Unclassified = Net Cash Change and Beginning Cash + Net Cash Change = Ending Cash; compare the latter to a balance-sheet cash total built from the SAME approved account set.
8. Test synthetic cases on disposable target-version MySQL: before/on/after cutoff, credit transactions, partial settlement, deposit application, return, unsold inventory, depreciation/disposal, losses, internal transfers, close/reopen period, and abnormal balances. Financial write tests never target the public sandbox. Build the fixture from the real schema, not from what the labels suggest: `DESCRIBE` every table you insert into and read the actual enum members, the NOT NULL columns with no default (audit columns like `dibuat_oleh` are frequently required), and the foreign keys that demand a parent row first (a sale needs a customer, and a customer needs a region). Register every COA account the scenario posts to in the fixture chart — the posting service rejects an unregistered code, so a missing account surfaces as a misleading scenario failure instead of the defect under test. Keep each scenario's assertions in one script and extend it for a related criterion rather than adding a near-duplicate branch. For a reusable synthetic database, generate data only in the disposable MySQL run, export a logical dump after all assertions pass, restore it into a second empty schema, and compare journal, COA, and period counts before retaining it. Keep any persistent test volume on an internal network without published ports and stop its container when idle; require an explicit target check before running destructive fixture scripts. Run a combined pass of related env-gated tests after individual passes: isolated scripts may each own the same COA primary keys, so their intersection can fail despite each test being green. Never call a passing synthetic fixture a reconciliation of actual PBJ balances.

Acceptance criteria to prove on the fixture, each as its own assertion: transactions after the cutoff do not change an earlier period's statement; a period with no transactions reports zero rather than borrowing another period's figures; opening balances are not double-counted; a reversal is accounted for by its own date; internal transfers do not inflate gross cash movement; a deposit is not counted twice when used to settle an invoice; profit for the period equals the change in equity (absent owner transactions); ending cash in the cash-flow statement equals the same cash classification on the balance sheet; and subledger detail reconciles to COA or shows a traceable difference. Criteria phrased as a falsifiable number catch defects that a code review reads past — the two that found real bugs in this project were the cross-period reversal check and the gross-transfer check.
9. Roll out narrow changes on `sandbox`, compare old/new statements on an authorized copy with explained differences, retain rollback, then verify authenticated UI and export figures. Do not infer render or ledger correctness from login HTTP 200, Blade compile, or Vite build.
10. Period locking: audit for the control before promising a closed period. Grep `app/` for `tutup_periode`, `periode_terkunci`, `before_or_equal`, and backdate guards. Journal dates flow straight from request input into the posting service, and operational controllers accept any `required|date` that later drives an accrual journal, so a backdated edit relocates a journal to another period. Report the absent control and the questions it needs (who may close, who may reopen, how the reason is recorded) — do not build locking, a period table, or a backdate guard on your own initiative; these are owner decisions. Once the owner has chosen the granularity (per year is simpler and matches his stated preference; per month matches monthly statements), the shape that works is: one small `periode_akuntansi` table keyed by year with an enum status, a controller with `tutup`/`buka` actions, and enforcement as a shared gate inside the posting service for callers that actually use it, plus an audit of direct `jurnal_umum` writers and source-document edit/delete paths that bypass that service. Gate BOTH directions: reject a new posting dated inside a closed year AND refuse reversal of a journal whose original date is inside a closed year as a separate closed-period control. A reversal dated today affects today's period, not the historical statement when reports include each original and reversal by its own date; do not claim otherwise. Also check that the reversal's own posting year is open. Make the gate tolerant of the table being absent (`Schema::hasTable` guard) so a runtime that has not migrated yet, and every pre-existing test branch, keeps working instead of failing on a missing table. Opening a closed period must require a written reason, an authorized role on the server-side route, and a persisted audit record; if the audit helper swallows exceptions or returns null, verify the audit insert and make the transition fail atomically when audit persistence fails. Check close/reopen idempotency as well as concurrent close-versus-post and close-versus-direct-update: a pre-transaction `exists()` check is a time-of-check/time-of-use race. Start the posting transaction before checking the period (`DB::transactionLevel() > 0`), create its unique year row if absent, and lock that row through commit; closing must lock the SAME year row before counting/updating. Any controller calling `pastikanPeriodeTerbuka` directly must invoke it INSIDE an active database transaction (`DB::beginTransaction()` or `DB::transaction()`), never before opening the transaction, so the row lock is held. When testing period locks in a runner that tests subsequent operations in the current year (`date('Y')`), always explicitly reopen the current year at the conclusion of the lock scenario (`$tutup($tahunHariIni, 'terbuka');`), otherwise later test branches in the same run fail due to a closed current year. Check both the original and reversal-posting years when reversing. Exercise two processes against disposable MySQL, calling the real close/reopen controller rather than duplicating its algorithm, and assert posting before close commits while posting after close is rejected. Audit all direct ledger updates, deletes, and backdated source edits; the shared posting guard alone cannot protect paths that bypass it. Migration is additive: a new table only, never a change to journal or COA rows, so historical data is untouched by design — verify that with row counts before and after. Prove the gate with falsifiable tests (post into a closed year, adjacent open year, reverse a closed-year journal, direct update/backdate, reopen with audit, and concurrent close/post); disable the gate only inside the disposable container and require the targeted test to fail. Related and still owner-owned: `balikJurnal` dates the reversal to today rather than the original period, so reversing a January journal in October books the reversal in October. That behaviour is consistent and must not be changed unilaterally; the consequence changes which period absorbs the correction.
11. A reconciliation page (subledger vs COA) is read-only by design: it compares operational tables to dated COA balances and displays each difference as an open item. Never let it post a balancing journal. Align subledger queries to the exact report cutoff date (`$tanggalCutoff`), not live status: for receivables (`list_piutang`), filter `tanggal_terbit <= $tanggalCutoff` and subtract payments from `riwayat_pembayaran_piutang` where `tanggal_bayar <= $tanggalCutoff`; for factory liabilities (`rilisan_pembelian_sig`), filter `tanggal_do <= $tanggalCutoff` (or `tanggal_so <= $tanggalCutoff` when DO date is null). Cover bank (linked `kode_akun` per `data_rekening` row), receivables (invoices minus payments through cutoff), factory payables, inventory and the asset register only where their dated movements permit an as-of reconstruction. Current `saldo_rekening`, invoice `status_piutang`/`sisa_piutang`, current `status_rekonsiliasi`, master stock × last purchase price, and current asset totals are NOT historical balances merely because the COA side has a cutoff; label unsupported periods 'data historis belum memadai' instead of comparing incompatible dates or showing zero. Assert the page leaves the journal row count unchanged, and state plainly that a difference can come from unposted transactions, differing recognition, or unverified classification — not only from error.
12. Supplier liability & AP settlement workflows: distinguish raw-material quarry liabilities (e.g., `30306` Hutang Supplier Kuari/Tambang with dedicated settlement helpers `jurnalPelunasanHutangTambang`) from factory cement liabilities (`30303` Hutang SIG). In PBJ's architecture, purchasing cement on credit records via `PembelianSOController` with method `hutang_sig` (Debit `10301` Persediaan Gudang, Credit `30303` Hutang SIG). Settling `30303` occurs either indirectly via credit line top-ups (`jurnalTopUpCL` to `10108`/`10109`) or directly via dedicated AP settlement actions (`jurnalPelunasanHutangSIG` in `PembelianSOController`: Debit `30303`, Credit `1010x` Bank PBJ under closed-period check and atomic account balance reduction). When adding settlement UI, prefer embedding modals/cards directly in existing functional modules (e.g. Pembelian SO alongside CL top-up) to minimize menu bloat while adhering strictly to existing UI themes (slate borders, font-mono numbers, dark mode, no decorative emojis). Cash-flow classification for any `30303` settlement is strictly Operating Cash Outflow (payments to suppliers). In as-of subledger reconciliation, `30303` reconciles against unreconciled factory delivery orders (`rilisan_pembelian_sig`), not ordinary supplier invoices.

For user-facing plans, write a readable file covering confirmed findings, assumptions, phased scope, acceptance criteria, rollback, and decisions requiring accountant/owner approval. Keep speculative dashboards behind the integrity gates.
