# PBJ financial-reporting audit and delivery gates

1. Read routes, reporting controller, views, journal service, and all posting callers before proposing calculations. Compare workspace controller to deployed runtime before claiming a finding applies to the sandbox. Record which statements are code facts versus unverified transaction-level risks.
2. Establish the effective date and treatment of opening balances; compare journal mutations to operational sources including cancellations, reversals, deposits, returns, and backdates. Require an explicit cutoff convention before historical reports. When comparing `saldo_berjalan` against `saldo_awal` plus signed journal mutations, report mismatched accounts as reconciliation exceptions, not proven misstatement: imported/seeded balances and missing history can produce the same observation. Compute the signed mutation with a subquery that joins `jurnal_umum` to `data_kode_akun`: the normal side (`saldo_normal`) lives on `data_kode_akun`, so referencing it inside a `jurnal_umum`-only subquery fails with `Unknown column 'saldo_normal'`. Then split the mismatches instead of treating them as one class — an account whose `saldo_awal` AND signed mutation are both zero while `saldo_berjalan` is nonzero has unexplained provenance; inspect seed/import paths, direct balance writes, and missing journal history before assigning a cause, because this observation alone does not identify its writer. Whole-table tells of the same: journal row count far below account count, and every journal date on a single day. Report both classes separately and never restate the total difference as a rupiah misstatement. Before interpreting ANY per-account difference, test whether the fixture's opening balances balance at all: sum `saldo_awal` separately for `saldo_normal = 'Debit'` and `'Kredit'` accounts and compare the two totals (do the same for `saldo_berjalan`). When the seeded opening balances are themselves unbalanced by a material amount, no account-level difference can be read as a misstatement measure — report the fixture imbalance as the finding and stop, because every downstream comparison inherits it. Specifically flag opening balances in nominal/expense accounts (e.g. `506% Beban Penyusutan`) for provenance review against dated source records and any prior closing entries; neither the correct destination account nor the cause of a baseline imbalance can be inferred from the account name or the residual arithmetic alone. Also list accounts whose cached balance sits on the wrong side (negative on a debit-normal account): that is a legitimate value to display, not a defect to hide.
3. Trace all direct journal writers/deleters and page-load synchronizers before trusting the journal as immutable; a GET that syncs spareparts can mutate ledger data — remove all `sinkronkan*` from `index()` GET and expose it only as an explicit POST (e.g. `keuangan.akuntansi.jurnal.sinkron_sparepart` guarded to SPV_KEUANGAN via a manual button). On reversal, test both journal rows and cached COA balances: inserting an opposite entry without applying its delta atomically leaves cached balances stale. Lock original entries inside the reversal transaction so simultaneous cancellation cannot create duplicate reversals. After a reversal, the posting service's idempotency guard must match only journals that are still active (or NULL status on legacy rows): a guard that matches any row carrying the reference makes a cancelled reference impossible to re-post, so a corrected re-post silently returns the dead journal number instead of writing a new entry. Test post → reverse → re-post the same reference, not just post → reverse. Route every multi-row cancellation through ONE shared helper that selects the active journal numbers for a reference under `lockForUpdate` and reverses each, rather than repeating the select-and-loop at each caller. Before any existing PRT-* journal changes nominal or transaction date, reject changes touching a closed period (check both old and new dates), then prefer reversing and reposting through the shared journal service so the historical row stays traceable; if an approved transitional path still updates in place, require one transaction spanning the operational source edit and journal sync, period-row locks for both old and new dates, locked source/journal/COA rows, signed delta to `saldo_berjalan`, and an isolated test proving rollback and closed-period behavior. Let sync errors propagate rather than logging and returning success; a caught error after source commit leaves stock, source, and journal inconsistent. Reject a transition to zero while an active journal exists unless it is explicitly reversed, and constrain updates to active rows so prior reversal evidence is never modified. A standalone `lockForUpdate()` query outside a transaction does not protect the following update. Orphan PRT-* rows must be reversed through the shared service, never `DELETE`. Keep existing historical rows untouched; test a fresh post/reversal and duplicate-reversal rejection on disposable target MySQL. Enumerate every direct `jurnal_umum` delete site before editing any of them and classify each one by what it does to cached balances, then re-classify by whether the rows it touches can already be reversed. A site that computes the per-account delta and `increment('saldo_berjalan')` before deleting looks correct and is correct only while every row it reads is still active — because it reads ALL rows carrying the reference, including rows already marked `dibalik`, it re-restores balances that `balikJurnal` already restored, so cancelling a slip whose journal was reversed earlier moves the balance twice. Manual-delta-plus-delete is therefore NOT safe by construction: route these sites through the shared reversal helper too, and prove it with a post → reverse → cancel-sequence test asserting the balance is unchanged by the second operation. Convert the sites that delete rows without restoring cached balances (ritase accrual update and destroy, SPK sparepart deletion). For bulk synchronizers, skip orphan `PRT-*` rows instead of deleting them, and reverse a single orphan through the explicit POST path so the balance flip stays transactional. When the audit is done, re-grep for direct `jurnal_umum` writes and require the only remaining hits to be inside the journal service.
4. Use the journal as the statement source and operational tables as subledgers to reconcile. For a monthly trial balance, distinguish the COA's undated `saldo_awal` baseline from the opening balance immediately before the selected month; compute that period opening at the prior month's cutoff before labeling the column "Saldo Awal". Inspect the actual journal date column type before choosing a cutoff predicate: `DATE` accepts an inclusive end-date, while `DATETIME` needs an exclusive next-day boundary to retain late-day entries. Check each account's opening + signed period debits/credits = closing according to `saldo_normal`, then compare both opening-side and closing-side total debit versus credit; balanced current-period mutations alone cannot certify a trial balance when the baseline is unbalanced. Add XLSX from the same calculated report rows as screen/CSV rather than a separate query; write account codes/names explicitly as strings (including names beginning `=`) and signed amounts explicitly as numbers, then reopen the streamed workbook and compare rows, cell types, negative balances and totals to the controller result. When a screenshot supplies a formal spreadsheet reference, extract hierarchy, right-aligned figures, borders, negative notation, and page size—not its numerical values, spreadsheet errors, or accounting method. Confirm whether it is only a visual reference before changing a direct cash-movement report into an indirect profit-adjustment statement. Keep download endpoints behind the existing report role gate; check the actual named routes and streamed XLSX after wiring a button. For PhpSpreadsheet print settings, fit one page wide with `setFitToHeight(0)` when the report may grow, so Excel can paginate vertically without shrinking to a fixed page count; inspect the resulting pages before promising a specific count. Consult the spreadsheet library's current documentation for uncertain cell-type or streaming behavior, and explain the relevance of the selected rule rather than citing it as accounting policy. Inspect screen, print and CSV footers: never put the debit–credit movement *difference* under a column headed "Saldo Akhir" or call the movement-only footer a balanced closing trial balance. Before displaying any live amounts, compare worktree and runtime hashes and establish whether the data are sandbox or production; query read-only aggregates without emitting private account rows, and report only status/counts unless values are explicitly needed. Reconcile bank, receivables/payables, inventory, and asset register to COA. Show unexplained differences, never a balancing plug.
5. P&L: compare revenue categories, discounts/returns, HPP at sale (not purchase), depreciation expense and operating expense by identical periods; preserve losses as negative. For a presentation-only redesign, inspect the existing controller totals and view before editing, then prefer an accessible bridge/waterfall of period revenue → HPP → gross profit → operating expense → operating profit → other income/expense → pre-tax profit when those are the actual supported stages. Datawrapper's waterfall-chart guide (`https://www.datawrapper.de/blog/waterfall-charts-guide`) is a useful reference for distinct totals, change categories and readable value labels; inspect the live reference before adopting it rather than copying its styling blindly. Show the exact signed amount for every stage even when its bar is tiny or zero, and give losses a clear baseline/sign. Keep the financial account detail, source drill-through, CSV, official print and mobile layout; do not change report arithmetic or rename pre-tax profit as after-tax profit to fit a chart. Assert each plotted stage against the controller's existing totals and the CSV ending amount on disposable synthetic data, then inspect desktop/mobile and print in a real browser. Distinguish unknown unit-specific sales volume from journal-derived monetary totals; never combine heterogeneous quantities into a single volume axis. Tax estimates require approved policy and applicable law, not an assumed flat rate: remove hardcoded flat percentages (e.g., 11%) from controllers and Blade views, present operating profit as the journal-derived figure pending tax verification, and recognize tax expenses only when backed by posted tax journal entries with clear memo disclosure. Trace every view tab, summary badge, print view, trend label, and CSV export for stale claims of after-tax profit, healthy margins, or completed reconciliation; changing the central table alone leaves misleading claims elsewhere. Do not expose a hardcoded zero as `bebanPajakRiil` or a duplicate `labaBersihSetelahPajak` while tax is unknown, because even hidden controller fields can be reused as apparent facts. Render the real Blade with controller data and assert both required disclosure and absence of unverified claims; compare every screen/print total and label against the CSV's final row, not merely its tax disclosure. CSV must use actual newline separators and quote fields so commas in values do not shift columns. Grep the reporting controller for prefix predicates (`like '101%'`, `like '506%'`) before trusting any grouped total: a code-range predicate silently absorbs whatever accounts fall in that range, pulling restricted-fund accounts into cash and depreciation EXPENSE accounts into accumulated depreciation, and no test of the report's arithmetic will reveal it. Build a coverage map for every posting account to its statement section and rendered detail. Prefer maintained account classifications over a new hard-coded whitelist; test ordinary revenue, other income, all HPP categories, operating/other expenses, and contra accounts. Compare account-level rows to subtotals in actual screen/print/CSV output: a controller total can include material revenue that the view never lists, and aggregated material HPP must not be labelled as cement HPP. A green total assertion does not establish complete presentation.
6. Balance sheet: gross assets, credit-normal accumulated depreciation, liabilities, contributed capital, dated retained earnings and current result. Watch for double recognition after closing entries and accidental inclusion of depreciation expense in accumulated depreciation. Calculate balance sheet cutoff per end of selected month (`Y-m-t`) from dated opening balances plus all posted journal mutations, including originals and reversals at their respective dates: querying real-time `saldo_berjalan` leaks subsequent months into earlier balance sheets. When a statement helper filters journal rows by `status_jurnal`, drop that filter: excluding non-active rows removes the ORIGINAL journal from its own period while its reversal lands in a different period, so a reversal dated in a later month makes the earlier period lose the transaction entirely. Count every journal row by its own `tanggal_transaksi` — the original stays in its period and the reversal subtracts in the period it was posted — and prove it with a cross-month reversal test asserting the earlier period's figure is unchanged and the later period nets to zero. Period membership and reversal treatment are separate concerns: filtering on status is not a substitute for dating. Also check that every view rendering these totals reads the helper's dated field (`saldo_cutoff`) rather than the stale `saldo_berjalan` column, or the page silently mixes dated and real-time figures. For accumulated depreciation, strictly filter for `kelompok_akun = 'Akumulasi Penyusutan'` or credit-normal `202%` accounts and strip fallback reads to operational tables (`riwayat_penyusutan`). Preserve the signed contra-asset balance and signed net asset value: `abs()` on abnormal debit balances and `max(0, gross − contra)` mask exceptions. Show the abnormal sign and warning in the rendered balance sheet; test both a debit-sided contra-asset and negative net asset on disposable MySQL. Replace a removed fallback with a visible reconciliation panel. Compare COA and the operational register only when their entity coverage and effective date match; otherwise show the available dated COA amount, label any current register snapshot separately, and keep the historical subledger and difference null with an explicit unsupported state. Do not calculate a current-versus-cutoff difference merely to replace the fallback with another misleading number. For contributed capital and retained earnings, sum the real COA accounts (`tipe_akun = 'Modal'`) plus accumulated revenue minus accumulated expense to the cutoff, so equity reflects real balances and any imbalance surfaces in the view's discrepancy banner (`$selisihNeraca`). In P&L, aggregate revenue (`Pendapatan`) from journal credit mutations within the selected calendar month and verify all active revenue accounts (such as `40404 Pendapatan Penjualan Material Alam`) are mapped rather than dropped; calculate HPP (`Harga Pokok Penjualan`) and operating expenses (`Beban Operasional`) from journal debit mutations within that same date range instead of using `max()` against operational tables or falling back to un-dated running balances.
7. Cash flow: enumerate actual cash-equivalent accounts; classify dated cash movements into operating, investing and financing; remove internal transfers; distinguish credit sales/purchases from receipts/payments and deposit receipts from deposit utilization. Reconcile beginning cash + movement = ending cash. Eliminating internal transfers means removing them from the GROSS inflow and outflow lines, not merely letting them net to zero: a transfer between two cash accounts shows as matching debit and credit, so the net figure looks correct while both gross lines inflate and every ratio built on them is wrong. Detect a transfer as a journal whose every line posts to a cash account and exclude the whole journal number from the gross aggregates, leaving ending cash untouched. For a revenue line, check how the posting service writes it before subtracting a discount again: when the journal credits the revenue account with the NETTO amount, subtracting the invoice discount from a journal-derived revenue total double-counts it — surface the discount as a memo line labelled as already included, and assert revenue equals the sum of journal credits. Beginning cash comes from the position BEFORE the period, not from ending cash minus a movement figure. Map cash movements to Operating, Investing, or Financing only after checking every counterpart row (`barisLawan`), the source document, and the approved cash-account definition; a `202%` prefix can also contain contra-assets, and a mixed journal cannot safely be assigned by the first matching counterpart. Keep unknown or mixed transactions in an explicit Unclassified bucket rather than defaulting all others to Operating. Classify a journal with multiple distinct counterpart accounts as unknown until source evidence supports a split; do not automatically promote it merely because every counterpart shares an account category, since their allocation and source may differ. A first-match asset account can silently label the entire cash movement as investing. Treat a direct cash/HPP counterpart as unclassified pending its source document (HPP recognition is usually noncash); distinguish bank principal liability from supplier liability before assigning financing versus operating. Guard an empty approved cash-account list before generating `IN (?, ...)`, and render an explicit 'account mapping unavailable' warning rather than interpreting calculated zero as actual cash. Assert the unclassified amount appears in the rendered page as well as the controller, and label still-heuristic operating/investing/financing totals provisional. Verify Operating + Investing + Financing + Unclassified = Net Cash Change and Beginning Cash + Net Cash Change = Ending Cash; compare the latter to a balance-sheet cash total built from the SAME approved account set.
8. Test synthetic cases on disposable target-version MySQL: before/on/after cutoff, credit transactions, partial settlement, deposit application, return, unsold inventory, depreciation/disposal, losses, internal transfers, close/reopen period, and abnormal balances. Financial write tests never target the public sandbox. Build the fixture from the real schema, not from what the labels suggest: `DESCRIBE` every table you insert into and read the actual enum members, the NOT NULL columns with no default (audit columns like `dibuat_oleh` are frequently required), and the foreign keys that demand a parent row first (a sale needs a customer, and a customer needs a region). Register every COA account the scenario posts to in the fixture chart — the posting service rejects an unregistered code, so a missing account surfaces as a misleading scenario failure instead of the defect under test. Keep each scenario's assertions in one script and extend it for a related criterion rather than adding a near-duplicate branch. Before copying a test under a new directory into an image-built disposable app, create its destination directory inside the test container; a copy/setup failure is not a RED accounting assertion. Verify the RED failure names the intended old-code balance defect after fixture setup, then run GREEN against the exact candidate. If a dirty controller contains unrelated authorization changes, construct the index blob from the tested source minus those hunks, copy `git show :<controller-path>` into the disposable app with a hash check, and rerun the fixture against that staged blob before QC or commit; worktree GREEN alone does not prove the narrower commit. For a reusable synthetic database, generate data only in the disposable MySQL run, export a logical dump after all assertions pass, restore it into a second empty schema, and compare journal, COA, and period counts before retaining it. Keep any persistent test volume on an internal network without published ports and stop its container when idle; require an explicit target check before running destructive fixture scripts. Run a combined pass of related env-gated tests after individual passes: isolated scripts may each own the same COA primary keys, so their intersection can fail despite each test being green. Never call a passing synthetic fixture a reconciliation of actual PBJ balances.

Acceptance criteria to prove on the fixture, each as its own assertion: transactions after the cutoff do not change an earlier period's statement; a period with no transactions reports zero rather than borrowing another period's figures; opening balances are not double-counted; a reversal is accounted for by its own date; internal transfers do not inflate gross cash movement; a deposit is not counted twice when used to settle an invoice; profit for the period equals the change in equity (absent owner transactions); ending cash in the cash-flow statement equals the same cash classification on the balance sheet; and subledger detail reconciles to COA or shows a traceable difference. Criteria phrased as a falsifiable number catch defects that a code review reads past — the two that found real bugs in this project were the cross-period reversal check and the gross-transfer check.
9. Roll out narrow changes on `sandbox`, compare old/new statements on an authorized copy with explained differences, retain rollback, then verify authenticated UI and export figures. Do not infer render or ledger correctness from login HTTP 200, Blade compile, or Vite build.
10. Period locking: audit for the control before promising a closed period. Grep `app/` for `tutup_periode`, `periode_terkunci`, `before_or_equal`, and backdate guards. Journal dates flow straight from request input into the posting service, and operational controllers accept any `required|date` that later drives an accrual journal, so a backdated edit relocates a journal to another period. Report the absent control and the questions it needs (who may close, who may reopen, how the reason is recorded) — do not build locking, a period table, or a backdate guard on your own initiative; these are owner decisions. Once the owner has chosen the granularity (per year is simpler and matches his stated preference; per month matches monthly statements), the shape that works is: one small `periode_akuntansi` table keyed by year with an enum status, a controller with `tutup`/`buka` actions, and enforcement as a shared gate inside the posting service for callers that actually use it, plus an audit of direct `jurnal_umum` writers and source-document edit/delete paths that bypass that service. Gate BOTH directions: reject a new posting dated inside a closed year AND refuse reversal of a journal whose original date is inside a closed year as a separate closed-period control. A reversal dated today affects today's period, not the historical statement when reports include each original and reversal by its own date; do not claim otherwise. Also check that the reversal's own posting year is open. After a correction moves a replacement journal into the current period, retain and gate the original source-document date as well as the active journal and proposed posting dates inside the transaction. Prove this boundary with source in an earlier open year → correction posted now → close the source year → attempt another source edit; reject the last operation without source, stock, bank, or journal changes. Checking only the latest replacement journal's year lets it launder a source transaction out of the closed-period control. Make the gate tolerant of the table being absent (`Schema::hasTable` guard) so a runtime that has not migrated yet, and every pre-existing test branch, keeps working instead of failing on a missing table. Opening a closed period must require a written reason, an authorized role on the server-side route, and a persisted audit record; if the audit helper swallows exceptions or returns null, verify the audit insert and make the transition fail atomically when audit persistence fails. Check close/reopen idempotency as well as concurrent close-versus-post and close-versus-direct-update: a pre-transaction `exists()` check is a time-of-check/time-of-use race. Start the posting transaction before checking the period (`DB::transactionLevel() > 0`), create its unique year row if absent, and lock that row through commit; closing must lock the SAME year row before counting/updating. Any controller calling `pastikanPeriodeTerbuka` directly must invoke it INSIDE an active database transaction (`DB::beginTransaction()` or `DB::transaction()`), never before opening the transaction, so the row lock is held. When testing period locks in a runner that tests subsequent operations in the current year (`date('Y')`), always explicitly reopen the current year at the conclusion of the lock scenario (`$tutup($tahunHariIni, 'terbuka');`), otherwise later test branches in the same run fail due to a closed current year. Check both the original and reversal-posting years when reversing. Exercise two processes against disposable MySQL, calling the real close/reopen controller rather than duplicating its algorithm, and assert posting before close commits while posting after close is rejected. Audit all direct ledger updates, deletes, and backdated source edits; the shared posting guard alone cannot protect paths that bypass it. Migration is additive: a new table only, never a change to journal or COA rows, so historical data is untouched by design — verify that with row counts before and after. Prove the gate with falsifiable tests (post into a closed year, adjacent open year, reverse a closed-year journal, direct update/backdate, reopen with audit, and concurrent close/post); disable the gate only inside the disposable container and require the targeted test to fail. Related and still owner-owned: `balikJurnal` dates the reversal to today rather than the original period, so reversing a January journal in October books the reversal in October. That behaviour is consistent and must not be changed unilaterally; the consequence changes which period absorbs the correction.
11. A reconciliation page (subledger vs COA) is read-only by design: it compares operational tables to dated COA balances and displays each difference as an open item. Never let it post a balancing journal. Align subledger queries to the exact report cutoff date (`$tanggalCutoff`), not live status: for customer receivables (`list_piutang`), filter `tanggal_terbit <= $tanggalCutoff` and identify the actual customer-payment relation by tracing its model, foreign keys, and payment controller before subtracting dated settlements. Do not use `riwayat_pembayaran_piutang` merely because of its name: it belongs to employee receivables (`PiutangKaryawan`), and overlapping numeric `id_piutang` values can silently subtract an employee's instalment from a customer's invoice. If customer-payment history is absent or incomplete, mark that cutoff unsupported rather than substituting another domain's history; for factory liabilities (`rilisan_pembelian_sig`), filter `tanggal_do <= $tanggalCutoff` (or `tanggal_so <= $tanggalCutoff` when DO date is null). Cover bank (linked `kode_akun` per `data_rekening` row), receivables (invoices minus payments through cutoff), factory payables, inventory and the asset register only where their dated movements permit an as-of reconstruction. Current `saldo_rekening`, invoice `status_piutang`/`sisa_piutang`, current `status_rekonsiliasi`, master stock × last purchase price, and current asset totals are NOT historical balances merely because the COA side has a cutoff; label unsupported periods 'data historis belum memadai' instead of comparing incompatible dates or showing zero. Assert the page leaves the journal row count unchanged, and state plainly that a difference can come from unposted transactions, differing recognition, or unverified classification — not only from error.
12. Supplier liability & AP settlement workflows: distinguish raw-material quarry liabilities (e.g., `30306` Hutang Supplier Kuari/Tambang with dedicated settlement helpers `jurnalPelunasanHutangTambang`) from factory cement liabilities (`30303` Hutang SIG). In PBJ's architecture, purchasing cement on credit records via `PembelianSOController` with method `hutang_sig` (Debit `10301` Persediaan Gudang, Credit `30303` Hutang SIG). Distinguish topping up CL SIG (`jurnalTopUpCL`, Debit `10108`/`10109` against Bank) from paying Hutang SIG: a CL top-up is not settlement of `30303` unless a separate documented liability-reduction entry exists. Verify dedicated settlement actions (`jurnalPelunasanHutangSIG` in `PembelianSOController`: Debit `30303`, Credit `1010x` Bank PBJ under closed-period check and atomic account balance reduction). When adding settlement UI, prefer embedding modals/cards directly in existing functional modules (e.g. Pembelian SO alongside CL top-up) to minimize menu bloat while adhering strictly to existing UI themes (slate borders, font-mono numbers, dark mode, no decorative emojis). Cash-flow classification for any `30303` settlement is strictly Operating Cash Outflow (payments to suppliers). Define the `30303` subledger from its actual debt recognition and settlement events. Do not assume unreconciled factory delivery orders (`rilisan_pembelian_sig`) equal unpaid supplier liabilities: delivery reconciliation status and payment status are different concepts and must be proved equivalent before comparing their totals.

## Opening-balance staging and target corrections

1. Inspect the current revision's routes, controllers, services, views, COA schema/classification, report query and approval middleware; verify whether the named opening-balance/target feature actually exists before describing its current behavior. Mark each statement as code evidence, isolated test evidence, or proposed design.
2. Preserve the existing operational journal engine, `saldo_awal + dated journal mutations` report formula, journal-integrity checks and draft/approval separation. Treat staged opening balances as balanced journal entries: the real account is paired with one explicitly designated temporary Opening Balance Equity (OBE) account, so an incomplete migration state can still balance without changing the posting engine or historical base fields.
3. For a target-balance correction, read the current account balance at the approved effective date, compute `target − current` using that account's normal-side sign, then post only the resulting delta against OBE in a balanced journal. Do not write the target into `saldo_awal` while also posting the delta; the report formula would recognize both and double-count the correction. Require a repeat-submit/idempotency rule and verify exact stored debit-credit equality at currency precision.
4. Confirm OBE is a distinct temporary equity classification in reports. If the current report groups every account typed `Modal` into permanent capital, assigning OBE that type without a separate display rule can falsely present a temporary balancing amount as contributed capital. Keep OBE visible and identifiable; do not transfer its remainder to contributed capital or retained earnings until asset, receivable and liability balances are reconciled and an accountant approves the dated reclassification journal.
5. Write the proposal as preserved foundations → bounded revision → evidence/assumptions → binary acceptance tests → rollback and owner/accountant decisions. Test a partial opening-balance stage, a target above and below current balance, repeated submission, cutoff before/after the journal date, OBE separation from permanent equity, and the final approved reclassification on a disposable database. A plan or code search is not proof that the feature is implemented; a synthetic pass is not proof that historical company balances reconcile.

## Numerical and traceability falsification procedure

1. State the claim and expected number before probing. Reuse the disposable runner with only the needed env gates; if a combined run stops, label later branches **not executed**, then run those branches separately. Preserve both exit status and output. Do not equate an `assert` failure in a test with a production accounting defect until its expectation is checked.
2. Compare workspace and authorized runtime file hashes read-only when scoping a finding; matching hashes prove source parity, not that PHP-FPM loaded it or an authenticated workflow succeeded. Keep synthetic fixtures and reports private, never under a public web root.
3. Test money at the stored scale. Normalize/validate finite positive amounts and approved rounding once, then require exact debit-credit equality at that scale. Include a one-minor-unit imbalance and fractional values: a test such as `round(abs(D-C), 2) > 0.01` accepts a real one-cent difference. Apply the same exact-scale comparison to synchronizer no-op detection: `abs(old-new) <= 0.01` silently discards a legitimate one-cent revision. A DECIMAL database column does not eliminate PHP float arithmetic or rounding inconsistencies. Verify rejected entries leave both ledger and cached balances unchanged; distinguish rounded display totals from stored/export precision.
4. Test the real service, controller and rendered view, not only matching aggregates. Seed a nonzero representative of every account category, including material sales/HPP and other income. Parse the rendered table rows, assert their sum equals each subtotal, and compare screen/print/CSV account codes, signs and final totals. Treat a negative expense as a possible reversal/credit, not proof of bad arithmetic; trace its journal first. For a zero denominator, distinguish an undefined margin from a genuine zero-percent margin.
5. Test semantic identity, not matching integer IDs. Use distinct customers/employees with deliberately overlapping local receivable IDs; ensure each report reads only its own payment history. For every reported amount, verify navigation `report total → account detail → complete journal → source document/payment → correction/reversal`, preserving the selected period. A text reference or a badge labelled “Buku Besar” is not a working drill-through link.
6. Validate lifecycle intersections: post → revise → cancel → cancel again → delete; also cancellation followed by reactivation and revision across months. Assert stock, bank subledger, COA, source status and journal effects together. A cancellation that restores stock but retains operational rows can restore it again on delete. A payroll/ritase deduction may belong to a compound journal rather than a standalone payment reference; reverse the actual owner workflow instead of deleting one allocation and pretending the whole payment was cancelled.
7. When replacing in-place edits with reversal/repost, assert original amounts/dates remain unchanged, follow `nomor_jurnal_pembalik`, and account for the reversal's `REV-` reference. Do not query only the original reference and conclude the reversal is missing. Update old assertions that demanded the original row change, without weakening balance/period checks. With reversal dated today and repost dated to the old transaction, test both periods explicitly; do not silently backdate the correction or claim historical stability.
8. Make the check executable and trustworthy: use explicit exceptions or `php -d zend.assertions=1 -d assert.exception=1` and verify assertions are active. Provide schema-valid fixtures and read actual model table names before inserts. Cover each promised correction, not two happy paths for three changed workflows. Keep a missing late preflight, an atomic SQL increment, and a genuine unprotected read-modify-write distinct: rollback-protected downstream period validation is not automatically a bypass, and relative SQL updates are already atomic. Test duplicated submissions at the source-status/idempotency boundary rather than scattering locks without a demonstrated race.
9. Audit master-data edits as well as journal writers: changing a used account's `tipe_akun`, `kelompok_akun` or `saldo_normal` can reclassify/re-sign every historical report even when posted journals are unchanged. Check period controls, provenance, and approval before allowing such changes; a closed-year posting guard alone does not freeze statement interpretation.

## Bagas's financial-reporting acceptance target

- Interpret “seinformatif mungkin” as complete transaction coverage, searchable evidence, and correct calculations—not more explanatory prose, more menus, or decorative KPIs. Prioritize integrity and traceability over further UI expansion.
- Connect existing screens through `report amount → account detail → complete journal → source transaction/payment → supporting evidence → approval and correction history`; preserve the selected period and Direktur's read-only boundary. For a report opened by drill-through, provide a clear return link with the selected period; if the user requests direct sidebar access, add it under the existing authorized report menu rather than treating contextual links as a substitute. A sidebar entry with no selected account must open a usable report/filter state, not assume a `kode_akun` query parameter exists. For presentation-only corrections such as code–account-name spacing, inspect the screenshot and exact rendered pair first, preserve existing navigation, and change the smallest view markup; a proximity complaint is not permission to alter click behavior or accounting data. When explaining a voucher reversal to a non-accountant, describe original journal → cancellation entry → return to the same account/period as reading event history, not changing the past. Keep the navigation fix distinct from a “source document not found” warning: an unresolved database lookup is not proof that physical evidence is gone. Verify source diff and deployed view hash/Blade compilation, but describe authenticated visual behavior as unverified until actually viewed after login rather than claiming it from a build or login HTTP 200 alone. When the user is reviewing rapidly on the sandbox, prioritize the narrow visible patch and a short manual check over constructing a disposable browser fixture for a one-line visual change; reserve full browser fixtures for financial logic or consequential regressions.
- Judge completeness by reconciled detail and lifecycle evidence: every posted amount must have an identifiable source, detail must sum to displayed/exported totals, and edit/cancel/repeat/delete sequences must not duplicate or lose effects. Qualify correctness by the scenarios and data actually verified; do not promise absolute error-free accounting from synthetic tests.
- Keep ONE readable status document stating what is built, verified, incomplete, and the next bounded integrity gate. Reconcile it with the current plan after interruptions; never promote an audit recommendation or unfinished patch to completed implementation.

## Integration pitfalls and repeatable browser proof

- Require the **last, suite-specific success marker**, not exit code alone or any earlier `PASS`: Laravel console bootstraps may render a caught exception and still return exit 0. Enable PHP assertions explicitly. A partially executed suite is a failure.
- Test all selected financial scripts together against the same copied workspace. Use deltas against an observed baseline for later fixtures, and explicitly open/restore the synthetic years they own; do not weaken source-period controls to accommodate contamination from preceding scripts.
- Give each AR instalment a persisted journal reference, not `date('His')`. Same-second payments can collide and an idempotency guard can otherwise silently skip the second financial effect. Carry a stable payment token in the existing form so a repeated **partial** payment, not just a fully paid invoice, is rejected without creating a second bank mutation.
- Normalize Eloquent Carbon dates at the caller with `format('Y-m-d')`; keep the shared journal API strict. Casting a Carbon date to string can append a time and break valid cancellations after central validation is tightened.
- Exercise reversal at the reference column's maximum length. If `REV-` would exceed capacity, retain the source through the explicit original-journal relationship instead of truncating its identifier or accepting an un-reversible post.
- Treat `x-data` as both an HTML attribute and JavaScript: raw double quotes can terminate the attribute, and Blade HTML escaping does not safely escape JavaScript apostrophes. Use `Js::from`/`@js` for **all** data-bearing expressions, including prefixed labels and `x-show` search text. Browser-test an account containing an apostrophe, filters and the actual download button.
- Verify source links use their real nested route names and open successfully with the intended role. `Route::has(false)` quietly removes a broken link; a rendered reference/name is not a test. Do not widen Direktur's operational access merely to make a material link work; expose an allowed financial summary and mark unsupported evidence honestly.
- Require a financial audit snapshot to persist before deleting OR replacing source detail. Preserve old/new document totals, items and exact journal references, and show only a financial whitelist in the voucher. An edit that reverses GL but deletes operational item rows still loses evidence unless its audit snapshot is persisted atomically; prove audit-failure rollback on the real edit controller, not only delete.
- Validate repeated stock items by their **summed quantity per item code** under one transaction/lock on both create and edit. Per-line sufficiency checks pass when each line fits but the total overdraws stock. Use a negative test where each individual quantity is available and only their sum exceeds availability, then assert source, stock and GL are unchanged.
- Compare document header totals with the exact validated item quantities/prices used for journal rows. Reject malformed item JSON instead of silently treating it as empty and posting a lump-sum fallback. A hidden raw numeric input must not pass through a digits-only sanitizer: it changes decimal scale and removes negative signs. Trace the real form payload, then search sibling create/edit controllers for the same sanitizer before calling the issue fixed across a module. A parser-only reproduction proves conversion, not saved transaction effects; exercise the actual controller and assert source total, stock value and GL together, because a balanced journal can faithfully post the wrong upstream amount.
- Payroll payment verification:
  1. Trace single payment, batch generation, slip synchronization and cancellation before patching a bank guard; the same defect can survive in a sibling writer.
  2. Before claiming a positive-THP transfer valid, verify the selected bank exists, its explicit `kode_akun` resolves to the maintained Kas/Bank classification, and the GL credits that same account. Reject missing or non-cash mappings rather than guessing by bank name or selecting the first bank; sufficient funds and a balanced journal can still credit the wrong account.
  3. Exercise valid, absent, nonexistent, insufficient-balance, unmapped and non-cash-mapped bank selections through the actual payment owner. Clear stale flash errors, then assert the fresh rejection reason and unchanged slip, bank, GL, employee deductions, master and ritase snapshots; a prior error or empty row count can conceal an unrelated failure.
  4. Check batch sufficiency against aggregate THP and assert one aggregate bank debit. Preserve zero-THP settlements such as full kasbon deduction without inventing a bank outflow. Do not classify a late validation as a bypass when the enclosing transaction demonstrably rolls back every effect.
  5. Read back the exact credited account and stored amount after a valid payment, then repeat and cancel that newly verified payment to check for double movement. Preserve a representative earlier scenario's journal through later fixture cleanup; a combined suite can pass after erasing its own prior evidence.
  6. Keep old slips without bank-movement provenance as unresolved reconciliation items; the absence of a movement record does not prove that no real transfer occurred, and a historical refund cannot be inferred automatically. Require source evidence and approval for correction, and keep calculation, approval and payment distinct without adding an unapproved workflow.
- Keep cancelled status changes on the existing owner cancellation path; allowing `Dibatalkan` in a create/edit payload that still runs stock/posting loops creates cancelled documents with active financial effects. Align existing form choices with the server contract, without adding a new workflow.
- Never reuse a deleted source-detail number while historical ledger references survive. A gap-filling generator that checks only the current source table can make an old journal point at a new item. Check used ledger identities too, and test that old/new source refs are disjoint after revision.
- Retest date behavior after repairing identifier reuse: accidental reuse can previously have triggered a helper's reversal-history date heuristic. Pass the correction posting date explicitly from the source owner when a replacement has a new identity, preserve source-document dates, and test the full controller path rather than the sync helper alone.
- For browser tests, create a synthetic identity/session only in the guarded disposable database; never reuse active user sessions. Serve via `php artisan serve`, not `php -S ... public/index.php`, because the latter routes static JS through Laravel and may return login/dashboard HTML as JavaScript. Set the disposable APP_ENV/APP_URL deliberately; production force-HTTPS is not compatible with the plain-HTTP loopback harness.
- Keep the disposable DB on an internal network; if host-browser port publication on that network is unreachable, attach only the test app to a bridge as well and bind its published port to loopback. Do not expose the database or change live networking.
- Wait for actual mobile drawer geometry/transition completion before screenshots. `scrollWidth <= clientWidth` alone can pass while a partially translated sidebar covers the report. Capture scrollable report sections separately; `fullPage` does not expand an overflow-scrolling main element.

For user-facing plans, write a readable file covering confirmed findings, assumptions, phased scope, acceptance criteria, rollback, and decisions requiring accountant/owner approval. Keep speculative dashboards behind the integrity gates.
