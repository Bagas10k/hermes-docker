# PBJ project workflow

- Missing dropdown data: verify master rows → cached rows/options → controller payload → included modal → selected hidden value and actual `FormData`. Reproduce both an initially empty cache followed by master creation and a populated cache followed by edit/delete, using the real application on an isolated database. Exercise arbitrary valid IDs rather than assuming ID `1`. Do not blame migrations when the required schema and master rows exist, or explain the user's uninspected local environment as fact. Follow `references/invoice-catalog-cache.md` for the shared semen/rekening cache and payment-field recipe.

- Preserve MySQL as PBJ's database engine: the original dump identifies MySQL 8.0.30, and Bagas explicitly rejected the unapproved switch to MariaDB. Obtain explicit approval before changing engine or release series; do not equate MySQL 8.4 with restoring the original 8.0 deployment. Distinguish project configuration, disposable tests, and active runtime in completion claims. Prioritize the smallest verified fix over repeated status-only assurances: when asked to execute, edit and run a real check in the same turn, then report the observed result and what remains. Before EVERY shell call, set `workdir` to the exact repository path `/home/ubuntu/website-pbj` (or another verified real directory); never append placeholders or punctuation. The `pbj_app` container is image-built, not bind-mounted — verify branch-only changes in a disposable container first; copy files into `pbj_app` and re-lint there only when a live-sandbox update is explicitly in scope, never as an automatic consequence of a worktree edit; after copying a change that adds or renames ROUTES, run `php artisan route:clear` and `config:clear` then re-cache, because a production container serving `route:cache` keeps the old route table and `route:list --path=<new path>` reports no match even though the copied file is correct; Blade `view:cache` only compiles templates; exercise the real controller's view data and render it on disposable data to test `@foreach`/`@if` branches, rather than hand-filling a partial variable list that can omit required fields or bypass controller defects. After swapping views into a disposable image, clear its compiled views and compare source hashes before rendering, because baked compiled Blade can still execute the previous template; keep each tool call under ~8K tokens by splitting large cat/patch into multiple small calls to avoid stream timeout. If a call is rejected before execution, inspect its arguments and issue one corrected call immediately—repeating the identical invalid call cannot change its result. Do not wait for a loop guard or ask Bagas to say “continue.” If a check still blocks delivery, explain in clear Indonesian what failed, what was actually changed or deployed, and what remains unverified; never forward a generic English tool-loop message as the user-facing result.

- Inspect the active branch and remote divergence before editing `/home/ubuntu/website-pbj`; use `sandbox` for exploratory changes and merge/push to `main` only on explicit approval. When instructed to push to `main` while the local worktree on `sandbox` is dirty with uncommitted experiments, NEVER checkout `main`, stash, or reset the worktree: update the local `main` ref directly with `git branch -f main <candidate-ref>`, run `git push --dry-run origin main:refs/heads/main`, push via explicit refspec `git push origin main:refs/heads/main`, and confirm with fresh `git ls-remote --heads origin main` readback. When Bagas says "jangan pula bikin plan taks", execute the bounded repair steps directly without creating or rewriting extra planning files or task queues, reporting honest empirical test results immediately. Jika template merujuk spreadsheet eksternal, baca header rujukan tanpa mengeluarkan baris nyata; bandingkan dengan parser aktual. Bedakan panduan konseptual dari alat yang benar-benar ada: verifikasi fitur dashboard, skrip, container, jaringan dan target runtime sebelum memberi perintah siap-jalan; jangan eksekusi perubahan impor VPS tanpa otorisasi eksplisit. Distinguish commit, remote push, and live deployment; interpret a Git push request as branch publication, not automatic permission to copy files, restart services or migrate an active database. Stage an explicit reviewed manifest from a dirty worktree, excluding held candidates, runtime artifacts and unrelated mode changes. If a selected file mixes the approved feature with older work, isolate the approved hunks rather than staging the whole file. Test the resulting release tree independently: a passing full worktree does not prove the smaller Git package works, and a passing Git package does not prove compatibility with a divergent live runtime. Run `git diff --cached --check` after staging because new untracked files are absent from the earlier working-tree diff check; verify staged blobs match the selected tested sources before committing. Verify the exact remote branch SHA after a push using fresh Git/GitHub readback. Then close the user's request with the destination branch, commit link and verified outcome; do not replace the push result with a build-only report. Reuse evidence bound to unchanged sources and stop when the acceptance gates pass. Run an additional check only for a changed dependency, explicit user request or concrete missing gate—not to manufacture repeated progress notifications. - Rehearse migrations and regressions on a disposable instance of the **target engine/version** (MySQL for a MySQL VPS); never use the live `pbj` database as a test fixture. Register a new scenario in `scripts/test-mysql-isolated.py` as a selectable env-gated check and run its real standalone PHP script; extend an existing script for closely related assertions. Synchronize the current application, routes, views, and required migrations once in a shared disposable preflight, then refresh caches and verify critical hashes before executing selected checks. Copy EVERY exercised dependency, not only the entry point; keep scenario setup separate without duplicating divergent source-copy lists. Use `test-suite-integrity` for the general suite-isolation and assertion-runtime gates. The test image bakes in older copies of shared services (`MesinJurnalOtomatis`, `PencatatJurnalSparepartService`, controllers), so a branch that copies only the entry point silently tests stale code and reports PASS for behaviour that is not in the worktree; after copying, `sha256sum` the container's copy against the worktree file and fail the branch BEFORE running the scenario when they differ. When a scenario adds a dependency, include it in the shared synchronization preflight; keep checks independently selectable so a failed early scenario can be diagnosed without treating later checks as passed. Each env-guarded branch asserts on a substring of its PHP script's stdout, so when you extend a scenario script, keep the original opening words of its final `echo` and append to them: rewording the label breaks the wrapper even though the PHP itself still passes. Extend the existing scenario script for a closely related assertion instead of adding a near-duplicate branch. A full run rebuilds the container, migrates, seeds, then executes the scenario, so it takes several minutes: give the command a generous timeout, and when it promotes to a tracked background process, poll that process for the exit code and output tail rather than launching a second concurrent run. Assert the defect BEFORE the fix: a nonzero exit on the pre-fix run is what proves the branch exercises the bug, so a branch that never failed proves nothing. When you are testing a guard that never existed before (an authorization gate, a period lock, a new validation rule), there is no pre-fix run to compare against and a green scenario only proves the fixture agrees with the code: add an env-guarded red mode to the branch that neuters the guard INSIDE the disposable container after copying the file in (`docker exec APP sed -i 's/<the guard call>/\/\/ disabled/' <file>`) and assert the scenario then fails at the specific expected assertion. A branch whose scenario needs a NEW table must copy the migration in and run `php artisan migrate --force` in that branch before executing, and the production gate must tolerate the table's absence (`Schema::hasTable` guard) so every pre-existing branch keeps passing on an un-migrated runtime. A guard that reads the authenticated account cannot be exercised by a faked session: provision real accounts in the disposable container per role and assert the HTTP status code PLUS the resulting row count, so "rejected" and "nothing was written" are both measured. A 419 from an un-tokenized request measures CSRF, not authorization — bootstrap the session and carry a token before reading anything into the result. Because `pbj_app` is image-built rather than bind-mounted, a host-side edit is invisible to the runtime until an authorized live-sandbox deployment copies it in; lint inside that container after such a copy, and do not mistake worktree tests for runtime verification. Inspect the test connection and transaction boundaries first: a controller commit can escape a test's outer transaction. Keep demo seeders off production; never expose credentials, password hashes, or session IDs. For a MariaDB-to-MySQL move, never attach the MariaDB datadir volume to MySQL: use a new empty volume and a logical dump, validate unsupported collations and view definers, exact table counts plus business totals, a restored backup, and full application boot before cutover. Verify that Laravel's native schema loader uses a CLI compatible with the target authentication and TLS; manual baseline import followed by migrations does not prove automatic fresh startup. Keep the old database intact and writes frozen until cutover checks pass.

- Authentication & Super Admin accounts: The PBJ production database on Docker is MySQL/MariaDB (`pbj_db`), not SQLite. Application authentication uses `super_account` (for super admins) and `account` (for staff/employees) mapped through `SuperAccount` and `Pengguna` Eloquent models, while the default Laravel `users` table is unused. For account discovery, query only non-secret columns such as `id_super_account`, `username`, and `nama_pemilik` from `super_account`; omit password hashes and session identifiers from tool output. Create synthetic accounts only inside a guarded disposable test database, not as a shortcut to inspecting an active account-management screen. Login rate limiting (`LayananKeamananLogin`) tracks consecutive failed attempts in cache (`keamanan_login:user:<username>`), enforcing exponential lockouts (30s at 4 failures, doubling up to 24h) and returning `"Akses masuk akun ini dijeda demi keamanan"` on lock. Clear the limit with `Cache::forget('keamanan_login:user:<username>')` or `LayananKeamananLogin::resetJedaAkun($username)`. Testing authenticated endpoints behind the public reverse proxy (`/pbj`) requires setting proper host headers (`Host: www.jajandigital.web.id`, `Referer: https://www.jajandigital.web.id/pbj/login`) to receive correct session cookies (`path=/pbj`) and avoid 419 CSRF failures. When someone says a shared app link opens without login, test that exact root URL in a fresh cookie-free browser as well as a protected route with cookie-free HTTP, then distinguish a still-active browser session from anonymous access; a login-page 200 alone proves neither. Do not sign them out or invalidate their session just to test. For staff login, treat `account.status_aktif` and `data_karyawan.status_karyawan` as independent gates: allow only linked employee statuses `aktif`, `kontrak`, or `tetap`; deny `non-aktif`, `berhenti`, and dangling employee links. Keep Super Admin and intentionally unlinked accounts on their explicit auth paths. Centralize the effective check and force fresh account/employee reads at login, protected middleware, and session heartbeat so an already-authenticated stale model cannot survive a status change. Display effective login eligibility separately from the account flag used by the Super Admin toggle; never auto-enable the account when employee status changes back to active. Add an env-gated scenario to `scripts/test-mysql-isolated.py` and run it only against disposable `pbj_test`; assert login, active-session revocation, middleware, unlinked/Super Admin controls, and account-toggle semantics using schema-faithful synthetic fixtures. - Asset depreciation (`AsetPerusahaan` & `RiwayatPenyusutan`): Trace form defaults/hidden fields, server validation, saved asset values, monthly calculation, journal posting, and report classification together before editing. Validate positive cost, residual below cost, and useful life; distinguish an accounting estimate from a tax schedule. Map accumulated depreciation to contra-assets (credit-normal) rather than expense accounts; debit expense and credit contra-asset through the shared journal service. Guard acquisition date and unique `(kode_aset, periode_tahun, periode_bulan)` at the database boundary, since preflight existence checks can race. For reruns and backdated periods, define chronological posting and prior-period controls before trusting current `nilai_buku`; reject unsafe periods rather than silently skipping. Exercise fresh/upgrade and concurrent rerun cases against a disposable instance of the target MySQL version, then reconcile asset detail, journal, COA, and balance sheet.
