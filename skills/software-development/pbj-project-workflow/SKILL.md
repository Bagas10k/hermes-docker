# PBJ project workflow

- Preserve MySQL as PBJ's database engine: the original dump identifies MySQL 8.0.30, and Bagas explicitly rejected the unapproved switch to MariaDB. Obtain explicit approval before changing engine or release series; do not equate MySQL 8.4 with restoring the original 8.0 deployment. Distinguish project configuration, disposable tests, and active runtime in completion claims. Prioritize the smallest verified fix over repeated status-only assurances: when asked to execute, edit and run a real check in the same turn, then report the observed result and what remains. Before EVERY shell call, set `workdir` to the exact repository path `/home/ubuntu/website-pbj` (or another verified real directory); never append placeholders or punctuation. The `pbj_app` container is image-built, not bind-mounted — verify branch-only changes in a disposable container first; copy files into `pbj_app` and re-lint there only when a live-sandbox update is explicitly in scope, never as an automatic consequence of a worktree edit; after copying a change that adds or renames ROUTES, run `php artisan route:clear` and `config:clear` then re-cache, because a production container serving `route:cache` keeps the old route table and `route:list --path=<new path>` reports no match even though the copied file is correct; Blade `view:cache` only compiles templates, so to prove a new page renders with the variables its controller passes, call `view('<view>', $data)->render()` with a hand-built collection in tinker — compilation never exercises the `@foreach`/`@if` branches; keep each tool call under ~8K tokens by splitting large cat/patch into multiple small calls to avoid stream timeout. If a call is rejected before execution, inspect its arguments and issue one corrected call immediately—repeating the identical invalid call cannot change its result. Do not wait for a loop guard or ask Bagas to say “continue.” If a check still blocks delivery, explain in clear Indonesian what failed, what was actually changed or deployed, and what remains unverified; never forward a generic English tool-loop message as the user-facing result.

- Inspect the active branch and remote divergence before editing `/home/ubuntu/website-pbj`; use `sandbox` for exploratory changes and merge/push to `main` only on explicit approval. Distinguish commit, remote push, and live deployment; verify remote refs after a push.
- Preserve existing business features and visual design. Fix causal defects, not serial patches. The repo previously mixed an October 2 schema dump with historical migrations; use Laravel native schema baseline for fresh installation and retain historical migrations for upgrades.
- Rehearse migrations and regressions on a disposable instance of the **target engine/version** (MySQL for a MySQL VPS); never use the live `pbj` database as a test fixture. Add each new scenario to `scripts/test-mysql-isolated.py` as its own env-guarded branch (e.g. `PBJ_TEST_REVERSAL=1`) that `docker cp`s EVERY file the scenario exercises — the entry point AND every shared service, controller, or helper it calls — into the temporary container and runs a small standalone PHP script, rather than editing an existing branch. The test image bakes in older copies of shared services (`MesinJurnalOtomatis`, `PencatatJurnalSparepartService`, controllers), so a branch that copies only the entry point silently tests stale code and reports PASS for behaviour that is not in the worktree; after copying, `sha256sum` the container's copy against the worktree file and fail the branch BEFORE running the scenario when they differ. Adding a scenario that exercises a shared service means adding that service to the branch's copy list — separate branches keep one scenario's failure from masking another. Each env-guarded branch asserts on a substring of its PHP script's stdout, so when you extend a scenario script, keep the original opening words of its final `echo` and append to them: rewording the label breaks the wrapper even though the PHP itself still passes. Extend the existing scenario script for a closely related assertion instead of adding a near-duplicate branch. A full run rebuilds the container, migrates, seeds, then executes the scenario, so it takes several minutes: give the command a generous timeout, and when it promotes to a tracked background process, poll that process for the exit code and output tail rather than launching a second concurrent run. Assert the defect BEFORE the fix: a nonzero exit on the pre-fix run is what proves the branch exercises the bug, so a branch that never failed proves nothing. When you are testing a guard that never existed before (an authorization gate, a period lock, a new validation rule), there is no pre-fix run to compare against and a green scenario only proves the fixture agrees with the code: add an env-guarded red mode to the branch that neuters the guard INSIDE the disposable container after copying the file in (`docker exec APP sed -i 's/<the guard call>/\/\/ disabled/' <file>`) and assert the scenario then fails at the specific expected assertion. A branch whose scenario needs a NEW table must copy the migration in and run `php artisan migrate --force` in that branch before executing, and the production gate must tolerate the table's absence (`Schema::hasTable` guard) so every pre-existing branch keeps passing on an un-migrated runtime. A guard that reads the authenticated account cannot be exercised by a faked session: provision real accounts in the disposable container per role and assert the HTTP status code PLUS the resulting row count, so "rejected" and "nothing was written" are both measured. A 419 from an un-tokenized request measures CSRF, not authorization — bootstrap the session and carry a token before reading anything into the result. Because `pbj_app` is image-built rather than bind-mounted, a host-side edit is invisible to the runtime until an authorized live-sandbox deployment copies it in; lint inside that container after such a copy, and do not mistake worktree tests for runtime verification. Inspect the test connection and transaction boundaries first: a controller commit can escape a test's outer transaction. Keep demo seeders off production; never expose credentials, password hashes, or session IDs. For a MariaDB-to-MySQL move, never attach the MariaDB datadir volume to MySQL: use a new empty volume and a logical dump, validate unsupported collations and view definers, exact table counts plus business totals, a restored backup, and full application boot before cutover. Verify that Laravel's native schema loader uses a CLI compatible with the target authentication and TLS; manual baseline import followed by migrations does not prove automatic fresh startup. Keep the old database intact and writes frozen until cutover checks pass.
- For a blank or alleged-404 PBJ page, first distinguish the screenshot from the actual HTTP response and compare the public URL, Laravel named route, and unauthenticated redirect. Behind the public `/pbj` prefix, `request()->fullUrlWithQuery()` can build filter links from an internal path without `/pbj`; generate filter links from `route('…', array_merge(request()->query(), ['filter' => 'value']))` instead. Check all sibling filter links and preserve other query keys. Reproduce the wrong link, test the route-generated URL (including prefix), then verify Blade compile, runtime readback, and authenticated navigation when a session is available; login HTTP 200 or a redirect alone does not prove the filtered page renders. For a blank dashboard with HTTP 200 and full DOM, also inspect HTML nesting: an unclosed `x-cloak` modal can swallow `#kontenUtama` into a hidden ancestor.
- Treat the jajandigital PBJ publication as Bagas's live **sandbox for testing**, not automatically as the destination MySQL VPS. When he explicitly asks to apply a tested feature there, deploy the narrow code change promptly without waiting for a `main` merge or altering the database engine: inspect the running container's mounts and image, copy the existing files to a rollback directory, copy only changed app/view files into the container, run PHP syntax and Blade compilation, reload PHP-FPM (`docker exec pbj_app sh -c 'kill -USR2 1'`) when `opcache.validate_timestamps = 0`, then read back the changed files from the running container and check the public HTTP response. Container file copies are ephemeral across recreation; report that explicitly and ensure the next image build includes the committed change. When asked to "publis" or make the deployment durable on the sandbox, rebuild the app image (`docker build -t website-pbj-app:latest . && docker tag website-pbj-app:latest website-pbj-worker:latest`), recreate app/worker services via `docker compose up -d --no-deps app worker` in the background (compose recreation can be detected as a long-lived server by tool guards), poll until `pbj_app` is running healthy, and verify the baked image contains the latest commits before claiming publication. HTTP 200 on login proves availability, not an authenticated journal workflow. Never run financial write tests against the published sandbox DB when a disposable MySQL test can prove the rule.
- Remote branch naming & pulling: fetch remote refs before assuming case sensitivity (e.g. `Jarzx` vs `jarzx`); an invalid ref causes git to fail before fetching. When asked to pull a remote branch, merge into `sandbox` (never direct to `main`), verify merge base and incoming migrations before running them, take a logical dump of the sandbox database prior to `php artisan migrate`, and execute migrations with `--force` because sandbox runs under `APP_ENV=production`. Verify migration batches, new columns, rerun idempotency, and post-migration login HTTP 200 before reporting success.
- Visual proof and screenshot captures in live sandbox: When taking screenshots of authenticated pages or modals for Bagas, inspect proxy/cookie constraints before invoking browser tools. In this environment, Playwright cannot resolve external DNS or HTTPS properly when accessing local docker containers directly via IP without custom routing. The live sandbox is proxied via Node.js (`penelitian-pola-pikir-ai/server.js`) on `/pbj` rewrite with `SESSION_DOMAIN=www.jajandigital.web.id`. Navigate directly via the public URL `https://www.jajandigital.web.id/pbj/login`, perform standard credential fill (`spv_keuangan` / `password123` or `direktur_pbj` / `password123` for executive views), wait for navigation to complete, and then navigate to the target sub-route (e.g. `/keuangan/ap/pembelian-so`). When taking screenshots of newly introduced routes or Blade views, always run `php artisan route:clear && php artisan route:cache && php artisan view:clear` inside `pbj_app` and restart the worker/app if necessary, otherwise the runtime throws `RouteNotFoundException` (HTTP 500) causing Playwright to capture a 500 error page rather than the actual UI. Validate the visual output with `vision_analyze` to ensure zero layout shift, neat contrast, and strict theme compliance before sending `MEDIA:` paths to the user.
- Executive reporting & visual documentation deliverables: When Bagas asks for an executive/director summary with screenshots and explanations (e.g. as a compiled PDF), compile an HTML document referencing local screenshot assets with clean typography, A4 page styling (`size: A4; margin: 15-18mm; page-break-before: always;`), and clear functional descriptions under each visual artifact. Use headless Chromium (`page.pdf({ format: 'A4', printBackground: true })` via Playwright) to generate high-resolution PDF documents cleanly without installing extra heavy system utilities. Verify page structure and file size, and deliver the final document via native `MEDIA:` path. Proactively leverage parallel sub-agents (`delegate_task`) for multi-step exploratory, audit, or review workloads to avoid sluggish deliveries and minimize latency: Bagas explicitly demands high execution velocity and delegating parallel tasks rather than serializing all diagnostics in the main turn.
- Seed reference roles via `JabatanSeeder` without demo accounts/passwords. Keep `AutentikasiSeeder` off production.
- Dedicated exploration or module redesign uses branch `sandbox` tracked to `origin/sandbox`; never merge or push to `main` without explicit approval.
- Authentication & Super Admin accounts: The PBJ production database on Docker is MySQL/MariaDB (`pbj_db`), not SQLite. Application authentication uses `super_account` (for super admins) and `account` (for staff/employees) mapped through `SuperAccount` and `Pengguna` Eloquent models, while the default Laravel `users` table is unused. When inspecting or seeding super admin accounts, query `super_account` (`id_super_account`, `username`, `password`, `nama_pemilik`). Login rate limiting (`LayananKeamananLogin`) tracks consecutive failed attempts in cache (`keamanan_login:user:<username>`), enforcing exponential lockouts (30s at 4 failures, doubling up to 24h) and returning `"Akses masuk akun ini dijeda demi keamanan"` on lock. Clear the limit with `Cache::forget('keamanan_login:user:<username>')` or `LayananKeamananLogin::resetJedaAkun($username)`. Testing authenticated endpoints behind the public reverse proxy (`/pbj`) requires setting proper host headers (`Host: www.jajandigital.web.id`, `Referer: https://www.jajandigital.web.id/pbj/login`) to receive correct session cookies (`path=/pbj`) and avoid 419 CSRF failures.
- Asset depreciation (`AsetPerusahaan` & `RiwayatPenyusutan`): Trace form defaults/hidden fields, server validation, saved asset values, monthly calculation, journal posting, and report classification together before editing. Straight-line monthly expense is `(acquisition cost − residual value) / useful-life years / 12`, capped at book value minus residual; the displayed annual rate `100 / years` is informational, so derive it server-side rather than trusting a separately editable field. Validate positive cost, residual below cost, and useful life; distinguish an accounting estimate from a tax schedule. Map accumulated depreciation to contra-assets (credit-normal) rather than expense accounts; debit expense and credit contra-asset through the shared journal service. Guard acquisition date and unique `(kode_aset, periode_tahun, periode_bulan)` at the database boundary, since preflight existence checks can race. For reruns and backdated periods, define chronological posting and prior-period controls before trusting current `nilai_buku`; reject unsafe periods rather than silently skipping. Exercise fresh/upgrade and concurrent rerun cases against a disposable instance of the target MySQL version, then reconcile asset detail, journal, COA, and balance sheet. Do not claim financial safety from a formula-only test.
- Vehicle plate entry: inspect every caller of the shared three-part plate component before changing its layout or Alpine synchronization; keep labels above inputs, make placeholder examples visibly distinct from stored values, and show a full preview only after all segments exist. Never fabricate a plausible vehicle registration identifier when the user leaves it blank; use an explicitly pending state if the domain allows it. Do not turn an optional plate into a required field merely to remove a fabricated fallback: first check the business rule, DB constraints, and current multi-unit/edit flows, then validate the chosen policy consistently in browser, server, and storage. Hidden `required` controls can fail browser validation while their panel is hidden; validate the visible segments or at the server boundary and test category switches. Test one- and multi-unit submissions on disposable MySQL, including empty/partial/valid plates and duplicate registrations; rendering HTML and formula-only unit checks do not prove posting or persistence.
- Manual journals: inspect every caller of the shared posting service before adding a balance guard; keep the manual rule separate from automatic postings because a global rejection changes unrelated business flows. Show each selected COA account's current normal-side balance in the form, but recompute under a database row lock inside the posting transaction before accepting: a displayed balance can become stale between selection and save. Reject a manual Kas/Bank reduction when its resulting balance remains or becomes negative, but allow an increase that repairs an already-negative balance; warn rather than reject for other accounts, whose negative normal balance can be legitimate. Derive Kas/Bank membership from the maintained COA classification, not an unverified name substring. On rejection, report the account, current balance, attempted reduction, and shortfall in Indonesian; retain the form's old inputs and show a useful inline warning rather than only a generic modal. Check duplicate references before calling an idempotent posting service so a reused reference cannot be reported as a newly written journal. Test sufficient and insufficient balances, non-cash negative warning, rollback, and concurrent posts on a disposable MySQL instance; never test financial writes against live data. Do not call this financial guard complete merely because PHP syntax or Blade compilation passed; verify its journal writes and absence of writes on rejection.

Inspect the dropdown component's selected-value/hidden-input synchronization and whether its menu is clipped by modal overflow; a screenshot of a generic error dialog alone does not prove which dropdown fault occurred. Reproduce with a filled form, an empty nominal, and a selected account in an isolated test/browser, then apply the smallest fix at the actual boundary. Avoid altering a shared input/dropdown component for a single form without checking its other callers. If no session is available, report that limitation explicitly; a public login HTTP 200 and container file presence cannot prove the form works. For inline balance previews, verify change/input event propagation from nested Alpine components and the active modal's stacking/overflow in a browser; Blade compilation does not execute those handlers.

Keep the parent row as a single `<a>` (`.link-sidebar-item`) with `@click="tanganiKlikSidebar($event, $el); dropdownMaterialTerbuka = true;"`; use the landing route when that role has access, but bind its `:href` to the accessible child route for roles permitted only to view Asal Material. Avoid disconnected vertical tree lines (`border-l-2 ml-4 pl-3`); use `pl-11` indentation instead to align bullets naturally under the parent label without conflicting with PBJ's flat navigation aesthetic. Because PBJ's SPA navigation (`muatKontenDinamis` in `app.blade.php`) preserves the live sidebar DOM without re-rendering it from the server, any sub-menu items must be explicitly classed as `.link-sidebar-subitem` and synchronized in both `tanganiKlikSidebar` and `sinkronkanSidebarAktif`: `sinkronkanSidebarAktif` must query `.link-sidebar-subitem` against the incoming page's route, apply active styles (`link-sidebar-subitem-aktif font-semibold text-blue-600 dark:text-blue-400 bg-blue-50/80 dark:bg-blue-900/20` and ringed bullet `bg-blue-600 dark:bg-blue-400 ring-2 ring-blue-500/30`), clear inactive siblings, and force the parent Alpine dropdown state open (`indukDropdown._x_dataStack[0].dropdownMaterialTerbuka = true`), otherwise direct sub-menu navigation leaves the sub-menu unhighlighted and closed. When a child route is active, give the parent a distinct category-active class and update it in both click-time and fetched-page synchronization; clear that class on navigation away. PBJ's sidebar DOM persists across SPA visits, so server-side Blade classes alone cannot keep the category highlight or open state correct. In PBJ's domain model, distinguish formal store partners (`data_customer` / Toko PBJ with deposit, CBD, and credit ceilings) from walk-in project buyers (`master_pembeli_umum` / Pembeli Umum for raw quarry materials): non-store material transactions auto-record to `PembeliUmum` to feed POS cashier autocomplete and track buyer volume without polluting the contractual customer master. Cashier checkout totals must compute `max(0, subtotal - diskon)` with freight defaulting to 0, and cashier receipts (`cetak_nota_kasir`) should render freight lines only when positive (`> 0`).

Audit the actual route, controller, posting service, and view before recommending features; separate confirmed code defects from unverified financial misstatements. Run every ad-hoc probe script inside the disposable test container, never through `docker exec` against the running `pbj_app`: a throwaway script that deletes or reseeds rows destroys the sandbox when aimed at the live container, and the disposable container is the only place a mutating probe belongs. If the sandbox is damaged anyway, stop and report it with the affected table counts before touching anything — reseeding or restoring is itself a change to active data that needs his authorization. A passing Vite build is not financial verification. Establish dated opening balances and a journal-to-source-document map first, then compute balance sheets to a cutoff and income statements from period mutations, not real-time `saldo_berjalan` mixed with period tables. Never conceal mismatches with `max()` source selection, silent fallbacks, `abs()` on abnormal balances, or plug retained earnings; report reconciliation differences. Keep expense depreciation (`506%`) off contra-assets (`202%` credit-normal), and recognize HPP on sales rather than treating purchases as sold inventory. Derive cash flow from dated cash/bank movements, not paid-status sales plus all purchases; classify operating/investing/financing and eliminate internal transfers. Do not clip negative profit to zero or hard-code a tax estimate as statutory fact. Reconcile subledgers, bank accounts, and COA on an isolated copy before correcting historical entries. For a requested plan, deliver a readable file with evidence/bounds, prioritized phases, acceptance tests, rollback, and explicit policy decisions; a proposal is not implementation approval. Keep ONE human-readable status document (`docs/STATUS-LAPORAN-KEUANGAN.md`) written in plain Indonesian for Bagas and push the commit-hash/technical detail into a separate technical log he does not have to read; when he says the information is "pecah pecah" or confusing, he means the answer was scattered across chat messages and technical logs rather than collected into one readable document — consolidate, do not add another file. A damaged-sandbox report is a section in that document, not a separate message. When Bagas asks what the next stage is or whether the revision is finished, re-read his original acceptance criteria and current implementation, then answer from the stage ledger — done, verified, blocked, and ONE recommended next action with its gate. Never promote green synthetic tests, a menu, or a commit into 'financially complete': a missing dated opening balance, unexplained reconciliation difference, unclassified cash flow, untested direct journal writer/concurrent period lock, missing authenticated walkthrough, or unapproved VPS release keeps the corresponding criterion open. Correct an earlier overclaim explicitly rather than repeating it; do not answer with a fresh proposal or re-derive the plan. Prefer the slice that closes a written acceptance criterion over the one that adds surface: when a stage is blocked on an owner decision, spend the turn proving the criteria that need no decision (period-cutoff behaviour, empty-period handling, cross-statement agreement, internal-transfer elimination) and write those tests even when the code already looks right — the sessions that found real defects were the ones written to falsify a claim, not to confirm it. A check that passes against a fixture you built yourself proves only that the fixture agrees with the code. Run related test branches together as well as separately: independent branches can reuse COA/reference keys and fail only when combined. He restates the direction ("jangan sampai kehilangan arah") as a check that the gates still hold, so keep each slice inside the current gate and name any work that must wait for an accounting-policy decision he owns. When he points back at a document he supplied, re-read that file from disk before acting on it: his cached document path is the source of truth, and a session summary's paraphrase of the plan is not the plan — a stage executed from the summary drifts from the gates he actually wrote. - Tax architecture (PPN & PPh) is a requirements backlog, not implemented policy. Before adding tax accounts or form calculations, verify current Indonesian law, transaction tax status, invoice/bukti-potong evidence, applicable rates and bases, and accountant-approved treatment. Do not hard-code an assumed uniform PPN rate, PPh rate, or monthly PTKP cutoff: PPh 21 TER and year-end reconciliation differ, PPh 22/23 creditability depends on who is taxed/withheld, and final PPh is not a credit against corporate income tax. Distinguish tax withheld by PBJ (liability) from tax withheld from PBJ (prepayment) before posting. Validate the complete journal and form flow in an isolated database.
- For empty financial tables, check the unfiltered record count and the filtered result separately before changing copy or metrics: zero stored records means "belum dicatat," not proof that employees owe nothing; a nonempty store with zero matches needs a filter-specific message and reset action. Never catch a failed financial read and replace it with empty collections or Rp 0, because that turns an outage into a false financial assertion. Reuse the existing empty-table component once as a table row (do not wrap its `<tr>` inside another `<tr>`), pass its actual `pesan` prop, and render the controller/view read-only against the sandbox to verify the branch; use disposable MySQL for any write tests. Distinguish a KPI for indebted employees from the count of all active employees in its label.
- Role authorization (read-only roles such as Direktur): the client RBAC matrix in `app.blade.php` only hides UI and is NOT enforcement. Enforce a view-only role at the ONE middleware choke point every route passes through (`PeriksaJabatan`) instead of per controller: a controller-level guard covers one module while hundreds of write routes across the other modules stay open, which looks like a fixed boundary and is not one. Reject write methods (POST/PUT/PATCH/DELETE) with 403 for view-only roles while letting GET and self-service routes (e.g. `profil.perbarui`) through, and keep the allowed-role parameter working for modules that declare one. Prove it with an isolated test that drives the HTTP kernel per role across several modules and asserts the status code PLUS the absence of a database write, then prove the test actually measures the gate by disabling the guard inside the disposable container (`sed` the copied file) and requiring that run to fail — a guard test that never failed proves nothing. A first attempt returning 419 is measuring CSRF, not authorization: bootstrap the session and carry a CSRF token before drawing conclusions. Do not conclude from a session-faked request either — the middleware reads the logged-in account, so assert against real provisioned accounts in the disposable container, and when the sandbox has no account for that role, report the runtime gap instead of adding accounts to active data.
