# PBJ project workflow

- Preserve MySQL as PBJ's database engine: the original dump identifies MySQL 8.0.30, and Bagas explicitly rejected the unapproved switch to MariaDB. Obtain explicit approval before changing engine or release series; do not equate MySQL 8.4 with restoring the original 8.0 deployment. Distinguish project configuration, disposable tests, and active runtime in completion claims. Prioritize the smallest verified fix over repeated status-only assurances: when asked to execute, edit and run a real check in the same turn, then report the observed result and what remains. Before EVERY shell call, set `workdir` to the exact repository path `/home/ubuntu/website-pbj` (or another verified real directory); never append placeholders or punctuation. If a call is rejected before execution, inspect its arguments and issue one corrected call immediately—repeating the identical invalid call cannot change its result. Do not wait for a loop guard or ask Bagas to say “continue.” If a check still blocks delivery, explain in clear Indonesian what failed, what was actually changed or deployed, and what remains unverified; never forward a generic English tool-loop message as the user-facing result.

- Inspect the active branch and remote divergence before editing `/home/ubuntu/website-pbj`; use `sandbox` for exploratory changes and merge/push to `main` only on explicit approval. Distinguish commit, remote push, and live deployment; verify remote refs after a push.
- Preserve existing business features and visual design. Fix causal defects, not serial patches. The repo previously mixed an October 2 schema dump with historical migrations; use Laravel native schema baseline for fresh installation and retain historical migrations for upgrades.
- Rehearse migrations and regressions on a disposable instance of the **target engine/version** (MySQL for a MySQL VPS); never use the live `pbj` database as a test fixture. Inspect the test connection and transaction boundaries first: a controller commit can escape a test's outer transaction. Keep demo seeders off production; never expose credentials, password hashes, or session IDs. For a MariaDB-to-MySQL move, never attach the MariaDB datadir volume to MySQL: use a new empty volume and a logical dump, validate unsupported collations and view definers, exact table counts plus business totals, a restored backup, and full application boot before cutover. Verify that Laravel's native schema loader uses a CLI compatible with the target authentication and TLS; manual baseline import followed by migrations does not prove automatic fresh startup. Keep the old database intact and writes frozen until cutover checks pass.
- For an authenticated blank dashboard, do not repeatedly ask Bagas to run Chrome Console snippets or assume a URL/DNS error from screenshots. Check HTML element nesting first: a missing closing tag (e.g. `</div>` on an `x-cloak` confirmation modal) swallows `#kontenUtama` into a hidden dialog, rendering blank despite HTTP 200 and a full DOM. Verify layout structure with an ancestor test (e.g. `tests/test_dashboard_layout.py`).
- Treat the jajandigital PBJ publication as Bagas's live **sandbox for testing**, not automatically as the destination MySQL VPS. When he explicitly asks to apply a tested feature there, deploy the narrow code change promptly without waiting for a `main` merge or altering the database engine: inspect the running container's mounts and image, copy the existing files to a rollback directory, copy only changed app/view files into the container, run PHP syntax and Blade compilation, reload PHP-FPM (`docker exec pbj_app sh -c 'kill -USR2 1'`) when `opcache.validate_timestamps = 0`, then read back the changed files from the running container and check the public HTTP response. Container file copies are ephemeral across recreation; report that explicitly and ensure the next image build includes the committed change. HTTP 200 on login proves availability, not an authenticated journal workflow. Never run financial write tests against the published sandbox DB when a disposable MySQL test can prove the rule.
- Seed reference roles via `JabatanSeeder` without demo accounts/passwords. Keep `AutentikasiSeeder` off production.
- Dedicated exploration or module redesign uses branch `sandbox` tracked to `origin/sandbox`; never merge or push to `main` without explicit approval.
- Asset depreciation (`AsetPerusahaan` & `RiwayatPenyusutan`): Map accumulated depreciation to contra-assets (credit-normal) rather than expense accounts; debit expense and credit contra-asset through the shared journal service. Guard acquisition date and unique `(kode_aset, periode_tahun, periode_bulan)` at the database boundary, since preflight existence checks can race. For reruns and backdated periods, define chronological posting and prior-period controls before trusting current `nilai_buku`; reject unsafe periods rather than silently skipping. Exercise fresh/upgrade and concurrent rerun cases against a disposable instance of the target MySQL version, then reconcile asset detail, journal, COA, and balance sheet. Do not claim financial safety from a formula-only test.
- Manual journals: inspect every caller of the shared posting service before adding a balance guard; keep the manual rule separate from automatic postings because a global rejection changes unrelated business flows. Show each selected COA account's current normal-side balance in the form, but recompute under a database row lock inside the posting transaction before accepting: a displayed balance can become stale between selection and save. Reject a manual Kas/Bank reduction when its resulting balance remains or becomes negative, but allow an increase that repairs an already-negative balance; warn rather than reject for other accounts, whose negative normal balance can be legitimate. Derive Kas/Bank membership from the maintained COA classification, not an unverified name substring. On rejection, report the account, current balance, attempted reduction, and shortfall in Indonesian; retain the form's old inputs and show a useful inline warning rather than only a generic modal. Check duplicate references before calling an idempotent posting service so a reused reference cannot be reported as a newly written journal. Test sufficient and insufficient balances, non-cash negative warning, rollback, and concurrent posts on a disposable MySQL instance; never test financial writes against live data. Do not call this financial guard complete merely because PHP syntax or Blade compilation passed; verify its journal writes and absence of writes on rejection.
- For a journal form showing `The nominal field is required`, trace the rendered control from the Rupiah display input to the hidden `name=nominal` value and Laravel validation before changing the shared component; a valid-looking display can submit an empty hidden value. Inspect the dropdown component's selected-value/hidden-input synchronization and whether its menu is clipped by modal overflow; a screenshot of a generic error dialog alone does not prove which dropdown fault occurred. Reproduce with a filled form, an empty nominal, and a selected account in an isolated test/browser, then apply the smallest fix at the actual boundary. Avoid altering a shared input/dropdown component for a single form without checking its other callers. After a narrow live-sandbox deployment, verify the actual authenticated form flow when an authorized session is available: select a dropdown option, enter a formatted nominal, inspect the submitted hidden `nominal`/account values, and exercise validation without a financial write on live data. If no session is available, report that limitation explicitly; a public login HTTP 200 and container file presence cannot prove the form works. For inline balance previews, verify change/input event propagation from nested Alpine components and the active modal's stacking/overflow in a browser; Blade compilation does not execute those handlers.
- COA feature-link filters: first trace the actual posting code and its COA identifiers in the shared journal service and feature controllers; distinguish a code referenced by a system feature from an account with transaction history or a nonzero balance. When Bagas asks for just a filter, add only a read-only filter beside the existing COA type/search controls; preserve their combined query semantics and existing totals. Use Bagas's approved COA dropdown copy: "Semua akun", "Akun terintegrasi", "Akun lainnya"; do not rename "Akun terintegrasi" to "Terhubung ke fitur" or claim that these accounts have transaction activity. Derive integration from verified posting references, not account names or nonzero balances. Test representative fixed accounts (including retail/curah and sales), unlinked accounts, and combined type/search filters on disposable MySQL; compile the Blade and verify the selected option survives a GET. For a themed dropdown, reuse the existing `<x-dropdown-kustom>` beside the type filter rather than introducing a native `<select>` with mismatched menu chrome; check that the ancestor panel does not clip the floating menu (`overflow-hidden`), then verify the expanded menu and selected state in a browser. A green Vite build is only an asset check, not proof that the Blade/Alpine dropdown renders or filters. If the COA mapping is hard-coded, inspect changed posting callers whenever adding a new account so the filter does not silently drift. Do not add badges, schema fields, status toggles, or dashboards unless requested.
- Financial reporting (Neraca): query gross fixed assets via `kode_akun like 202%` with `saldo_normal = 'Debit'`, and accumulated depreciation via `saldo_normal = 'Kredit'` / `kelompok_akun = 'Akumulasi Penyusutan'`, preventing expense account contamination on asset book values. Historical balance sheets must compute opening balance + journal mutations up to the selected cut-off date, not read real-time `saldo_berjalan`. Laba Ditahan must bind directly to cumulative net income from Laporan Laba Rugi, never calculated as a plug number (`Aktiva - Kewajiban - Modal Disetor`) which conceals unrecorded journals. Reconcile physical bank accounts (`data_rekening`) against COA cash/bank (`10101`–`10109`) and support allowance for bad debt (`10204`) for receivables overdue > 90 days.
- Tax architecture (PPN & PPh) is a requirements backlog, not implemented policy. Before adding tax accounts or form calculations, verify current Indonesian law, transaction tax status, invoice/bukti-potong evidence, applicable rates and bases, and accountant-approved treatment. Do not hard-code an assumed uniform PPN rate, PPh rate, or monthly PTKP cutoff: PPh 21 TER and year-end reconciliation differ, PPh 22/23 creditability depends on who is taxed/withheld, and final PPh is not a credit against corporate income tax. Distinguish tax withheld by PBJ (liability) from tax withheld from PBJ (prepayment) before posting. Validate the complete journal and form flow in an isolated database.
- UI/UX refinements must adhere strictly to "Warm Paper & Obsidian" (`bg-white dark:bg-[#14161F] border-[#E2E8F0] dark:border-[#252837]`), rounded-3xl modals with `backdrop-blur-sm`, and zero emojis. Always run `git diff --check` and `npm run build` before pushing.
- Keep reports honest: HTTP 200 and populated DOM do not prove visible rendering; a green build or default-order Feature suite does not prove financial correctness. State test counts, database isolation, remote push, and deployment status separately. If asked whether the DB was originally MariaDB, compare the initial repository dump/config and current runtime; a MySQL 8 dump migrated into MariaDB is not evidence that the original engine was MariaDB. Bagas clarified that the destination VPS still uses MySQL and PBJ has not been installed there: prepare and verify the MySQL deployment path directly, without assuming the development server's MariaDB must be migrated or touched. Distinguish the destination VPS from the currently running PBJ environment before changing either. For financial advice, flag assumptions and correct oversimplifications rather than presenting a tax analogy as law.
