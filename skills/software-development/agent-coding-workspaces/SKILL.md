# Agent coding workspaces

## Procedure
1. Establish the user's primary outcome and first usable slice: project-scoped native agent chat, file/diff inspection, session continuation, and existing approvals. Ask separately whether fresh reauthentication on every risky action is a hard launch condition; approval is not reauthentication. If the user prioritizes a comfortable vibe-coding surface, do not expand into a new execution engine before proving the native chat workflow.
2. Inventory the real runtime and routing boundary. Identify the actual public ingress process, dashboard backend, auth provider, WebSocket upgrade handler, profile, and project directory before editing a proxy. Do not infer the ingress from a similarly named service or local port. Check existing files and process ownership, then make a reversible route change with a rollback patch.
3. Create an isolated profile and disposable Git repository for staging. Pin both the profile's active project and terminal cwd to that repository; remove unrelated real projects from the profile's active list. Do not use a production repository as the first write-test target. Preserve credentials through the runtime's supported profile mechanism, never by printing secrets.
4. Use the runtime's own chat/TUI and approval prompts. If the requested experience is simply terminal-like chat, start with the existing Chat tab and a project-scoped profile; defer plugin panels, proxy routes, and a second transcript until the user actually needs them. Verify the spawned agent's project cwd, a real model response, and resume by explicit session ID. Do not infer workspace-scoped resume from a one-shot session until its persisted cwd/repository metadata is observed.
5. Separate read-only inspection from execution. A dashboard plugin's read-only route must fail closed without a verified interactive admin session, reject service/bearer principals when only browser admin access is intended, and limit path/command inputs on the server. Test the actual route in an unauthenticated app and behind host auth, not only a detached guard function. For mutation, inventory terminal, file write/patch, code execution, background processes, direct PTY/console, and plugin/connector paths before claiming coverage.
6. If per-action reauthentication is required, require a fresh server-verified credential event bound to the authenticated principal, exact live session, final action arguments, short TTL, and one-time consumption. A login cookie, WebSocket ticket, confirm button, or ordinary tool approval is not fresh reauthentication. Do not enable a partial guard that protects only one dispatcher while direct execution paths remain available; either close those paths in an isolated runtime or keep the feature disabled.
7. Verify in layers: unit tests, real host-auth middleware negative/positive tests, model-backed chat, browser login, one safe write in the disposable repository, diff after reload, denial without approval, and public ingress smoke. Let the user trigger password/login and judge the interactive UX in their own browser; do not seek credentials in chat. Report precisely which layer is unverified.
8. Deploy only the tested slice to the intended surface after confirming public route, login redirect, cookie prefix, asset URLs, POST login endpoint, WebSocket upgrade, and session continuity end to end. Test both direct origin and public HTTPS. Trace the actual browser request URLs after login: a server-rendered form may POST to absolute `/auth/...` even when its redirect is correctly prefixed, and chat may use `/api/pty` WebSocket rather than the separate gateway `/api/ws`. Scope every form action and WebSocket path to the isolated backend; verify each is authenticated and actually reaches that backend. A public 401 alone proves only the outer gate, not successful login or working chat. If a proxy route fails its post-login path, roll back the route instead of leaving a dead preview publicly advertised.

## Pitfalls
- Timebox architecture exploration and parallel investigations; switch to a smaller deliverable when a security requirement expands the project beyond the user's main UX goal, because repeated isolated tests do not create a usable workspace.
- Resolve the actual ingress chain before restarting a service; a similarly named process can own a different port, so a healthy local route need not be the public route.
- Treat path-prefixed auth as an end-to-end contract: login HTML, fetch URLs, redirect targets, cookies, static assets, and WebSocket URLs must all retain the prefix. A backend redirect with the right prefix does not prove the login form uses it.
- Treat a repository test failure as pre-existing only after reproducing it against unchanged data/code or showing its causal independence; run relevant focused tests and report the full-suite failure separately rather than silently fixing unrelated data.
- When terminal-like chat feels slow, time the exact turn rather than changing models or proxy settings on intuition: inspect persisted user/assistant timestamps, session usage and live transport state, compare a minimal new-session prompt, and separate first-token/model latency from a turn with no completion. A prior fast turn does not explain a later stalled turn. Never call a multi-minute missing reply merely normal model latency.
- Before applying a quick live proxy edit, establish a red-capable login→chat WebSocket check and a rollback; an HTTP login redirect or unauthenticated 401 does not exercise the interactive chat. Verify the correct running ingress service before restarting it.

## Delivery style for Bagas
Give the current working URL or artifact, what was actually exercised, and the single next blocker. Do not narrate every check or repeatedly announce that work is still running; when execution stalls, stop speculative parallel work and state the precise gap. Bagas prefers to trigger interactive login and UX tests himself: prepare a safe disposable repository, then ask him for the resulting URL or visible error, never the password/cookie. A screenshot of a reconnecting chat is evidence of a failed WebSocket path, not proof that login failed. Never direct a write test at a real business repository first.
